# 浏览器自动化模块设计

> 日期：2026-09-14
> 状态：设计阶段
> 关联：`doc/api.md`（Agent API）、`mederi/docs/architecture/01-core.md`、BrowserPilot 项目架构

## 〇、设计目标

为 mederi 增加自动化操作浏览器的能力。不是搬运 BrowserPilot，而是取其架构经验，适配 mederi 的 Koog + 项目 + MCP 体系。

**核心原则：**
- 主代理只派发浏览器任务、看状态，不看细节
- BROWSER agent 负责操作，BrowserBrain 负责判定，两者内部协作，主代理无感
- 用户通过独立 API/UI 看浏览器任务细节
- 浏览器控制抽象接口在 core，Camoufox（BiDi）是 core 默认实现，JCEF 是 app 层可选实现
- Camoufox 路径由用户在设置中配置，暂不提供下载能力
- 通用化：系统不知道"投简历"这个概念，RuleSet 的内容决定判定什么

## 一、异步子代理管理（前置改动）

### 1.1 问题

当前 `SubagentRunnerImpl.run()` 是阻塞的：`SpawnAgentTool.execute()` 调 `subagentRunner.run()` → 挂起等子代理跑完 → 返回结果字符串。父代理在整个子代理执行期间无法继续。

### 1.2 方案：SubagentManager

新建 `SubagentManager`，把 `SubagentRunnerImpl.run()` 的逻辑包进 `scope.launch {}`，返回 agentId 而非结果。

**新文件：** `core/.../tools/subagent/SubagentManager.kt`（约 120 行）

```kotlin
class SubagentManager(
    private val subagentRunner: SubagentRunnerImpl,
    private val scope: CoroutineScope
) {
    private val agents = ConcurrentHashMap<String, BackgroundAgent>()

    data class BackgroundAgent(
        val job: Job,
        val role: SubagentRole,
        @Volatile var status: SubagentStatus,
        @Volatile var result: String?,
        @Volatile var progress: String  // 最后一步做了什么
    )

    enum class SubagentStatus { RUNNING, COMPLETED, ERROR, STOPPED }

    fun spawn(
        task: String, briefing: String?, plan: String?,
        role: SubagentRole, workType: WorkType,
        directories: List<String>, aiModel: AIModel,
        reasoningLevel: ReasoningLevel, projectId: String,
        parentSessionId: String
    ): String {
        val agentId = "sub_${UUID.randomUUID().toString().take(8)}"
        val deferred = CompletableDeferred<String>()
        val job = scope.launch {
            val bg = BackgroundAgent(
                job = this.coroutineContext.job,
                role = role,
                status = SubagentStatus.RUNNING,
                result = null,
                progress = "starting"
            )
            agents[agentId] = bg
            try {
                // 复用 SubagentRunnerImpl 的全部逻辑
                val result = subagentRunner.run(task, briefing, plan, role, workType, directories, aiModel, reasoningLevel, projectId, parentSessionId)
                bg.result = result
                bg.status = SubagentStatus.COMPLETED
                deferred.complete(result)
            } catch (e: CancellationException) {
                bg.result = "[stopped] ${e.message ?: "cancelled"}"
                bg.status = SubagentStatus.STOPPED
                deferred.complete(bg.result!!)
                throw e  // 协程规范：重新抛 CancellationException
            } catch (e: Throwable) {
                bg.result = "[subagent error] ${e.message ?: e.javaClass.simpleName}"
                bg.status = SubagentStatus.ERROR
                deferred.complete(bg.result!!)
            }
        }
        return agentId
    }

    fun status(agentId: String): String {
        val bg = agents[agentId] ?: return """{"status":"NOT_FOUND"}"""
        return """{"status":"${bg.status}","progress":"${bg.progress}"}"""
    }

    fun stop(agentId: String): String {
        val bg = agents[agentId] ?: return """{"status":"NOT_FOUND"}"""
        bg.job.cancel()
        return """{"status":"STOPPED","partialResult":"${bg.result ?: ""}"}"""
    }

    suspend fun wait(agentId: String, timeoutMs: Long = 60000): String {
        val bg = agents[agentId] ?: return """{"status":"NOT_FOUND"}"""
        return try {
            withTimeout(timeoutMs) {
                while (bg.status == SubagentStatus.RUNNING) {
                    delay(200)
                }
            }
            """{"status":"${bg.status}","result":"${bg.result ?: ""}"}"""
        } catch (e: TimeoutCancellationException) {
            """{"status":"TIMEOUT","progress":"${bg.progress}"}"""
        }
    }
}
```

**关键点：** `SubagentRunnerImpl.run()` 的代码完全不动——它内部已经是 `suspend fun` + 阻塞等 eventBus 的模式。在 `scope.launch {}` 里调用它，它自然在后台协程里挂起等待，不阻塞调用方。

### 1.4 对现有 Plan Workflow 的影响

现有 plan workflow（create_plan → generate_spec → spawn_agent → verify_subtask）依赖 `spawn_agent` 的阻塞返回——主代理拿到执行报告后才 verify。

改为异步后，主代理有两种用法：

1. **需要结果才继续（plan workflow）**：spawn 后立即 `wait_agent(agentId, timeout=300)`
   - 行为等价于原来的阻塞，但主代理可以在 wait 期间响应中断
2. **不需要等（浏览器任务）**：spawn 后继续干别的，后面再查 status

提示词需要教 LLM 区分这两种场景。对 plan workflow，指导 LLM 在 spawn 后发 `wait_agent`。

### 2.2 浏览器控制接口

```kotlin
interface BrowserControl {
    fun navigate(url: String): OperationResult
    fun click(elementRef: String): OperationResult
    fun clickByCoordinates(x: Double, y: Double): OperationResult
    fun type(elementRef: String, text: String): OperationResult
    fun scroll(direction: ScrollDirection, amount: Int): OperationResult
    fun press(key: String): OperationResult
    fun snapshot(): PageSnapshot          // a11y tree → YAML
    fun screenshot(): String?            // base64，可选
    fun getCurrentUrl(): String
    fun getTitle(): String
    fun close()
}

data class PageSnapshot(
    val url: String,
    val title: String,
    val yaml: String,           // CLEAN 模式 a11y tree（紧凑 YAML）
    val rawTree: Any?           // 原始树（供 refId 重映射用，执行后即丢）
)

sealed class OperationResult {
    data class Success(val message: String) : OperationResult()
    data class Failure(val message: String) : OperationResult()
    object Acknowledged : OperationResult()
}

enum class BrowserType { CAMOUFOX, JCEF }  // 用于 awareness（日志/事件），不驱动选择
```

**两个实现，分属不同层：**

| 实现 | 层 | 适用场景 | 反检测 | 来源 |
|---|---|---|---|---|
| `BiDiBrowserControl` | **core**（默认） | 内核直接操作浏览器 | 是 | 从 BrowserPilot **直接 copy** BiDi 层（BiDiBrowser/BiDiPage/BiDiTransport/BiDiSnapshot/BiDiModels/BiDiJsScripts），改造适配 mederi 的 `BrowserControl` 接口 |
| `JCEFBrowserControl` | **app/desktop**（可选） | 桌面版 UI 可视化操作 | 否 | app 层实现，注入 core |

**注入机制：**

```kotlin
// MederiConfig（core 层）
data class MederiConfig {
    ...
    var camoufoxPath: String? = null              // 用户在设置里填 Camoufox 目录
    var browserControlFactory: (() -> BrowserControl)? = null  // app 层注入（JCEF）
}

// BrowserTaskManager 创建控制实例
private fun createBrowserControl(): BrowserControl {
    // app 注入了 factory → 用它（JCEF）
    // 没注入 → 用 BiDiBrowserControl(camoufoxPath)，camoufoxPath 空就报错
    return config.browserControlFactory?.invoke()
        ?: BiDiBrowserControl(
            config.camoufoxPath ?: error("Camoufox 路径未设置，请在设置中配置 Camoufox 目录")
        )
}
```

**关键设计：**
- core 默认用 Camoufox（BiDi），这是内核能力，不依赖 UI
- app 层（桌面版）如果想用 JCEF，注入 `browserControlFactory` 即可
- core 知道 `BrowserType`（日志/事件标记），但不关心实现细节
- 不提供 Camoufox 下载——用户自行下载并配置路径
- 设置项：`camoufox.path`（Camoufox 目录路径）

### 2.4 BROWSER Agent（BrowserAgentRunner）

**不使用 Koog 的 ChatMemory 和 `mederiSingleRunStrategy`。** 使用 Koog 的 LLM client + 自定义循环 + 手动 prompt 管理。

**工具隔离：**
浏览器操作工具（navigate/click/type/scroll/snapshot/execute_drill/ask_browser_brain/done）是 BROWSER agent 的**内部 action 类型**，**不经过 `ToolFactory`，不注册到 Koog ToolRegistry**。它们只存在于 `BrowserAgentRunner` 内部，主代理和其他子代理永远看不到这些工具。

三套工具完全隔离：

| 工具集 | 谁可见 | 注册方式 | 示例 |
|---|---|---|---|
| 主代理工具 | 主代理 (EXECUTE/PLAN) | `ToolFactory.build()` | read_file, write_file, execute_command, spawn_agent, **run_browser_task**, browser_task_status, stop_browser_task |
| 浏览器操作 action | **仅 BROWSER agent** | `BrowserAgentRunner` 内部解析，不走 ToolFactory | navigate, click, type, scroll, snapshot, execute_drill, ask_browser_brain, done |
| BrowserBrain 工具 | **仅 BrowserBrain** | `BrowserBrainRunner` 内部 Koog ToolRegistry | write_drill, write_skill, save_procedure |

**每步 prompt 结构（参考 BrowserPilot）：**
```
[system: BrowserPrompt.build() — 工具说明 + 操作规则 + skill operatorContent]
<agent_history>          ← 最后 10 步的紧凑文本（系统维护）
<agent_state>
  <user_request>          ← 任务
  <memory>                ← AI 自总结（上一步的 decision.memory）
  <step_info>             ← 当前步/最大步
</agent_state>
<last_action_results>     ← 上一步的结果（发完即焚）
<browser_state>
  <url>
  <active_tab_snapshot>   ← 新鲜 a11y tree YAML（用完即丢）
</browser_state>
<rule_set>                ← 当前选中的 RuleSet 内容（可选，供 BROWSER 参考）
```

**循环逻辑（4-phase）：**
```kotlin
suspend fun run(task: String, ...) {
    val state = BrowserTaskState(task = task, memory = task)
    repeat(maxSteps) { step ->
        // Phase 1: PERCEIVE
        val snapshot = browserControl.snapshot()

        // Phase 2: DECIDE
        val userPrompt = buildUserPrompt(state, snapshot, stepHistory, ruleSet)
        val response = llmClient.chat(systemPrompt, userPrompt)  // Koog LLM client
        val decision = parseDecision(response)  // {action, memory, is_done}

        state.memory = decision.memory

        // Phase 3: EXECUTE
        val results = mutableListOf<ActionResult>()
        for (action in decision.actions) {
            when (action) {
                is NavigateAction -> browserControl.navigate(action.url)
                is ClickAction    -> browserControl.click(action.elementRef)
                is TypeAction     -> browserControl.type(action.elementRef, action.text)
                is ExecuteDrill   -> drillEngine.run(action.script)
                is AskBrain       -> browserBrainRunner.judge(action.content, ruleSet, action.instruction)
                is DoneAction     -> { return TaskResult(success = true, message = action.message) }
            }
        }

        // Phase 4: POSTPROCESS
        state.lastActionResults = results
        stepHistory.add(step, decision.thought, results)
        emit(BrowserEvent.StepCompleted(step, results))

        if (decision.isDone) return TaskResult(success = true, message = decision.doneMessage)
    }
    return TaskResult(success = false, message = "max steps reached")
}
```

**关键设计：**
- snapshot 每步新鲜取，不进历史
- `state.memory` 是 AI 自己写的摘要，没有单独的总结 LLM 调用
- `stepHistory` 是系统维护的紧凑文本，最后 10 步
- 浏览器操作不走 Koog 的 tool-calling loop，而是 LLM 一次输出所有 action + memory，`BrowserAgentRunner` 自己解析执行
- `ask_browser_brain` 是一个 action 类型，委托给 BrowserBrainRunner
- **工具隔离**：浏览器操作工具不经过 `ToolFactory`，不污染主代理工具集；主代理只看到 `run_browser_task` / `browser_task_status` / `stop_browser_task` 三个工具

**为什么不用 Koog tool-calling loop：**
BrowserPilot 验证了"一次 LLM 调用拿所有 action + memory"的模式比 tool-calling loop 更适合浏览器操作。tool-calling loop 会在一次 `agent.run()` 内累积所有 tool result（包括 page snapshot），而 BrowserPilot 的模式保证每步 prompt 完全重建，snapshot 不累积。

### 2.5 BrowserBrain（BrowserBrainRunner）

**无状态判定引擎，用最高智商模型。**

```kotlin
class BrowserBrainRunner(
    private val providerManager: ProviderManager,
    private val mcpConnector: McpConnector?
) {
    suspend fun judge(
        content: String,          // 浏览器 agent 采集的信息
        ruleSet: String,          // RuleSet 内容（判定规则 + 背景知识）
        instruction: String       // 本次判定指令
    ): String {
        // 每次调用完全独立，无历史
        val systemPrompt = BrowserBrainPrompt.build()  // 工具说明 + 输出格式要求
        val userPrompt = buildString {
            append("### [规则集]：\n").append(ruleSet).append("\n\n")
            append("### [待判定内容]：\n").append(content).append("\n\n")
            append("### [判定指令]：\n").append(instruction)
        }

        // 用 Koog 的 mederiSingleRunStrategy（tool-calling loop，最多 10 轮）
        // BrowserBrain 有文件工具：write_drill, write_skill, save_procedure
        val agent = buildBrainAgent(systemPrompt, userPrompt, brainTools)
        return agent.run(userPrompt)
    }
}
```

**关键设计：**
- 无记忆——每次调用从零开始，保证判定一致性
- 有文件工具——能帮 BROWSER agent 固化发现（write_drill, write_skill）
- 用 Koog 的标准 tool-calling loop——BrowserBrain 的工具循环适合 Koog
- 用 thinking model（高智商模型）

| `run_browser_task` | `task: String` | `{"taskId":"bt_xxx","status":"RUNNING"}` | 派发浏览器任务，立即返回 |
| `browser_task_status` | `taskId: String` | `{"status":"COMPLETED"}` | 只有状态，无细节 |
| `stop_browser_task` | `taskId: String` | `{"status":"STOPPED"}` | 停止任务 |

**主代理不需要 `wait_browser_task` 工具**——主代理不需要等浏览器任务完成。用户问"搜一下51job的工作"，主代理派发任务，继续跟用户聊天。任务完成后主代理下次查 status 看到完成，告诉用户。

### 3.2 提示词指引

```

你可以使用 `run_browser_task` 派发浏览器自动化任务。任务异步执行，你派发后可以继续与用户对话。

```

## 3.2 浏览器注册与选择（BrowserRegistry）

**注册模式**：全局 `BrowserRegistry`（commonMain）——UI 注册 JCEF、core 注册 Camoufox，AI 通过 `run_browser_task(browser=name)` 选择：

```kotlin
// core（MederiAiCore 启动装配）
BrowserRegistry.register("camoufox", BrowserKind.CAMOUFOX) {
    BiDiBrowserControl(binaryPath = installed, profilePath = profilesDir)
}

// UI（desktop 层）
BrowserRegistry.register("jcef", BrowserKind.JCEF) {
    JCEFBrowserControl(workspaceBrowserPage)  // 包住 UI 正在渲染的 KBPage
}

// AI 调用（工具参数）
run_browser_task(task, browser = "jcef")      // 测用户自己的网页 → 内置可见
run_browser_task(task, browser = "camoufox")  // 第三方自动化 → 无头反检测
```

- `BrowserKind(JCEF/CAMOUFOX)` 带人话 label，AI 可感知
- `BrowserTaskManager` 任务记 `browserName`，status 返回里带 browser（AI 知道任务跑在哪个浏览器）
- 工具描述**动态生成**：列出已注册浏览器 + 选择指引（测自己网页→jcef，第三方自动化→camoufox）
- `run_browser_task` 的 `browser` 参数缺省 → 用注册表默认（`defaultName` 或第一个）
- `BrowserControl.start/close` 语义：Camoufox 真拉起/关闭；**JCEF 均为幂等空实现**——任务结束
  （runner finally 总调 close()）不杀页面，tab 保留让用户看结果，手动关 tab 或应用退出才回收
- **工厂 suspend**：JCEF 创建 KBPage 需挂 Main 线程且 newPage 是 suspend；Camoufox 工厂仅构造对象
  （进程启动在 start()）。core 仅 jvm 目标 → 工厂注册两处（camoufox 在 MederiAiCore、jcef 在
  desktopApp main.kt）都在 JVM 侧，commonMain 不引用 core 浏览器类型
- **UI 自动展开**：desktop UI 注入 `UiBrowserHost`（tab=KBPage 轻量容器）到 `AppState.uiBrowserHost`
  （= `canRenderJcef`）；WorkspaceViewModel 监听 `BROWSER_TASK_STARTED(browser=="jcef")` 且
  canRenderJcef → 自动展开右侧 BROWSER 面板。遥控端/wasm 无宿主，不展开

## 五、关键设计决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| BROWSER agent 用 Koog ChatMemory？ | 否 | 每步重建 prompt，snapshot 不累积；ChatMemory 的累积模型不适合 |
| BROWSER agent 用 Koog 策略图？ | 是（自定义） | 用 Koog LLM client + 自定义节点管理 prompt；不用 mederiSingleRunStrategy |
| BrowserBrain 用 Koog？ | 是 | 标准 mederiSingleRunStrategy（tool-calling loop，最多 10 轮），适合文件工具 |
| 浏览器工具用 Koog Tool 系统？ | 否 | LLM 一次输出所有 action + memory（BrowserPilot 模式），不走 tool-calling loop；且工具隔离——浏览器操作工具不经过 ToolFactory，不污染主代理工具集 |
| Drill 用 LLM？ | 否 | 零 token 确定性执行；ask_ai 步骤才调 BrowserBrain |
| 异步子代理改动量 | ~300 行新 + ~65 行改 | SubagentManager 包装现有 SubagentRunnerImpl，不重写 |
| 主代理看浏览器任务细节？ | 否 | 主代理只有状态；用户通过独立 API/UI 看细节 |
| BrowserBrain 有记忆？ | 否 | 无状态保证判定一致性；每次调用完全独立 |
| Camoufox vs JCEF 分层 | core 默认 Camoufox，JCEF 在 app 层 | Camoufox 是内核能力；JCEF 是 UI 层可选集成 |
| Camoufox 下载 | 暂不实现 | 用户自行下载并配置路径 |
