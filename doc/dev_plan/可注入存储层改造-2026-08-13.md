## 一、背景与问题

### 现状

DataManager 对 **Session / History / ApiKey** 已经采用了正确的依赖倒置模式：构造函数注入 `SessionStore` / `HistoryStore` / `ApiKeyStore` 抽象，不持有数据载体，纯转发。注入谁，谁就是数据库。

但对 **Provider / Agent** 没有采用同样模式：

1. `DefaultDataManager` 内部 `new` 了两个 `ConcurrentHashMap` 作为数据载体，**不可注入**。
2. 依赖 `ConfigStore`，其接口是整存整取的 `loadProviders() / saveProviders(全量List)`——这是 JSON 文件模型的形状，不是数据库的形状。
3. 存储策略被焊死在操作逻辑里：`saveProvider` = 改内存 + 全量写 JSON。
4. `Mederi.kt` 中 `DataManager.init()` 未被调用（注释"暂时不调用 init()"），持久化模式下重启会丢 Provider/Agent。
5. `MederiConfig` 没有 `configStore` / `providerStore` / `agentStore` 注入点，`JsonConfigStore` 在 `Mederi.kt` 被无条件 new 出来。

### 设计声明（AGENTS.md）

- 场景 B：服务器端"不引入 mederi-sqlite，自己实现 HistoryStore"，企业"用自己的数据库（PostgreSQL/MySQL/MongoDB）"。
- 第 4 节："所有可替换组件通过构造函数/DSL 注入，显式可控。"

现状只对运行时数据兑现了声明，配置数据（Provider/Agent）未兑现。

## 二、设计目标

### 核心原则

**DataManager 只承载操作逻辑（校验、组装、合并、级联），不持有任何数据载体。** Provider/Agent 的数据载体抽象成可注入的 Store。注入谁，谁就是数据库。对方存成什么格式，是对方的私事。

### 硬约束

1. **存储分工不变**：本地默认实现里，Provider/Agent 仍存 JSON 文件，API Key / 对话历史 / Session 仍存 SQLite。
2. **接口不出现存储格式**：`ProviderStore` / `AgentStore` 接口只传 `Provider` / `Agent` 领域对象，不传 `String`/`Json`/`byte[]`。
3. **注入方自由**：接口对存储格式零假设。注入方存 JSONB / 关系表 / MongoDB / Redis / Protobuf 均可，DataManager 代码一行不改。
4. **本地高性能**：读配置命中内存缓存（零 IO）；写配置低频全量落盘（Provider/Agent 是低频配置）；对话历史热路径仍走 SQLite 增量。
5. **Model 内嵌 Provider 聚合**：不单独建 `ModelStore`。`getProvider` 单次 Store 调用即拿到 Provider + 全部 Model，保证最低往返次数。注入方在库内如何存 Model（JSONB 列 / 子表）是它的自由。
6. **API 层与 DataManager trait 零改动**：`ProviderApiImpl` / `AgentApiImpl` 等对着 `DataManager` 抽象编程，感受不到底层变化。这是依赖倒置落地的验证点。
7. **避免 N+1**：`ModelApiImpl.list/get` 等不需要 keys 的调用路径，不得触发 keys 查询。
8. **引用完整性软策略**：配置层不强制外键。删 Provider/Model 后，引用它的 Agent 允许 `modelId` 悬空，运行时再校验——与现有"URL 不纠错"理念一致。

### 三档优先级（与现有 History/Key/Session 一致）

显式注入 > configDir（内置 JSON）> 纯内存（InMemory）

## 三、接口设计

### 新增接口

```kotlin
// store/ProviderStore.kt
interface ProviderStore {
    suspend fun list(): List<Provider>          // 不含 apiKeys（keys 由 ApiKeyStore 管，读时由 DataManager 合并）
    suspend fun get(id: String): Provider?
    suspend fun save(provider: Provider)       // upsert：按 id 插入或整条覆盖
    suspend fun delete(id: String)
}

// store/AgentStore.kt
interface AgentStore {
    suspend fun list(): List<Agent>
    suspend fun get(id: String): Agent?
    suspend fun save(agent: Agent)              // upsert
    suspend fun delete(id: String)
}
```

### 决策记录

- **`save` 做_upsert_，不拆 insert/update**：API 层（`ProviderApiImpl.addModel` 等）已是"构造完整对象再整体保存"模式，upsert 匹配现状，且对数据库友好（`INSERT ... ON CONFLICT` / `UPDATE`）。
- **Model 不独立成 Store**：性能最优（单次往返），聚合根完整性由 DataManager 保证。`addModel` = 读 Provider → 改 models → `saveProvider`。
- **apiKeys 仍由 `ApiKeyStore` 独立管理**（已是可注入好公民）。`Provider.apiKeys` 本就是 `@Transient`，`ProviderStore` 只存 Provider 本身，读时由 DataManager 合并 keys。
- **删除 `ConfigStore`**：其整存整取接口是 JSON 文件形状，会诱导错误用法。职责由 `JsonProviderStore` / `JsonAgentStore` 取代。
- **`ApiKeyStore.listByProvider` 返回顺序必须确定**（修订 3）：所有实现必须 `ORDER BY is_default DESC, created_at ASC`（默认 key 在前，再按创建时间升序）。`mederi.sq` 的 `listByProvider` 查询需补 `ORDER BY`。测试断言据此可安全使用下标，但仍优先用 `firstOrNull { it.isDefault }` 取默认 key 断言。
- **`JsonProviderStore` / `JsonAgentStore` 构造接收 `File`，不接收 `MederiPaths`**（修订 6）：避免 Store 实现依赖含 SQLite 路径的 `MederiPaths`，装配时由 `Mederi.kt` 传 `paths.providersFile` / `paths.agentsFile`。
- **JSON 写必须原子**（修订 7）：写临时文件 `providers.json.tmp` → `renameTo(providers.json)`，避免半写损坏。

## 五、测试标准（贯穿所有步骤）

> **"测试通过" ≠ "测试跑绿了"。**

1. **必须有仿真数据**：每条测试用例使用具体的、业务语义化的数据（真实的 provider 名、base URL、model 名、对话文本），不允许只用 `"test"` / `"a"` / 空字符串凑数。
2. **必须有具体值断言**：断言必须命中具体值（`== "OpenAI Prod"` / `size == 2` / `models[1].supportsThinking == true`），不允许只断言 `assertNotNull` / `isNotEmpty` / `assertTrue(x != null)`。
3. **必须验证持久化**：涉及 Store 的测试，必须"关闭实例 → 重开 → 数据可复现"，不能只在同一个内存对象上转圈。
4. **文件/数据库必须读到内容**：JSON impl 的测试必须读回文件文本断言字段；SQLite 的测试必须重开连接验证（现有 `SessionConversationFlowTest` 已是这个范式，沿用）。
5. **隔离性**：内存实现的测试必须验证两个实例互不可见。
6. **顺序确定性**：断言依赖集合元素顺序时，底层实现必须保证顺序确定（见《三、决策记录》中 ApiKeyStore 排序约定）；不确定时用筛选（`firstOrNull { it.isDefault }`）而非下标。

- **风险**：`Provider.apiKeys` 是 `@Transient`，JSON 往返不丢——已在现有代码验证，Step 2 测试会再次覆盖。
