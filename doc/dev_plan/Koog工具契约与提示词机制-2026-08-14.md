# Koog 工具契约与提示词机制

> 创建日期：2026-08-14
> 依据：Koog 1.1.1 **源码**（Gradle 缓存 `koog-agents-jvm-1.1.1-sources.jar`、`agents-core-jvm-1.1.1-sources.jar`、`agents-tools-jvm-1.1.1-sources.jar`），非文档推测。
> 回答四个核心问题：① Koog 接受的工具契约是什么；② 如何把工具给 Koog；③ 如何把工具使用方式的提示词给 Koog；④ Koog 有没有内置提示词。

---

## 零、结论速览

| 问题 | 结论 |
|---|---|
| 工具契约 | 继承 `ToolBase<TArgs, TResult>`（最常用 `SimpleTool<TArgs, TResult>`），实现 `execute(args)`，元数据放 `ToolDescriptor(name, description, requiredParameters, optionalParameters)` |
| 如何把工具给 Koog | 用 `ToolRegistry { tool(...) }` 收集工具实例，通过 builder 的 `.toolRegistry(registry)` 装配给 AIAgent；执行时每个工具的 descriptor 组成 `List<ToolDescriptor>` 结构化传给 LLMClient |
| 工具使用方式提示词怎么给 | **不写进 system prompt**。全部写在 `ToolDescriptor.description` 和 `ToolParameterDescriptor.description` 里，由 `OpenAICompatibleToolDescriptorSchemaGenerator` 生成 OpenAI 兼容的 tools JSON（type/properties/required）作为 API 结构化参数。工具结果文本由 `encodeResultToString()` 决定（可 override） |
| Koog 有没有内置提示词 | **agent 循环没有任何内置 system prompt**。系统提示词完全由我们通过 `Prompt.builder().system(...)` 创建。Koog 仅有少量「功能性内置注入」：ChatMemory 的 facts 消息、chat 策略的"别聊天快调工具"反馈、工具执行失败的错误文本、ReAct 的 reasoningPrompt |

## 一、Koog 的工具契约

### 1.1 继承体系（agents-tools 模块）

```
ToolBase<TArgs, TResult>   // 抽象基类：argsType/resultType/descriptor/metadata + 序列化 + execute
 ├── Tool<TArgs, TResult>   // 无 metadata 的 execute(args) 形态（现有工具多继承这个）
 │    ├── SimpleTool<TArgs, TResult>   // 最简封装：构造传 name + description
 │    └── ToolFromCallable              // 反射工具（@Tool 注解）
 └── AgentContextAwareTool              // 需要访问 AIAgentContext 的工具（在 agents-core）
```

**`Tool<TArgs, TResult>` 抽象类**（[Tool 接口文档](../../mederi/doc/koog-api-docs-md/agents/agents-tools/ai.koog.agents.core.tools/-tool/index.md)）核心契约：

```kotlin
abstract class Tool<TArgs, TResult>(
    argsType: TypeToken,
    resultType: TypeToken,
    descriptor: ToolDescriptor,     // 给 LLM 看的工具元数据（名 + 描述 + 参数）
    metadata: Map<String, String> = emptyMap(),
) : ToolBase<TArgs, TResult> {
    abstract suspend fun execute(args: TArgs): TResult   // 工具逻辑
    // ToolBase 提供：
    //   encodeResultToString(result, serializer): String  —— 结果展示给 LLM 的文本（可 override）
    //   encodeArgs / decodeArgs / encodeResult / decodeResult —— 序列化
}
```

用 `SimpleTool` 最省事：

```kotlin
class DatabaseQueryTool(private val db: DbConnection) : SimpleTool<DatabaseQueryTool.Args, String>(
    name = "db_query",
    description = "执行安全的 SQL 查询操作"        // ← 工具使用方式提示词
) {
    data class Args(val query: String)             // 参数名用 snake_case

    override suspend fun run(args: Args): String {
        return db.execute(args.query)
    }
}
```

### 1.2 ToolDescriptor —— 给 LLM 的全部工具元数据

```kotlin
public open class ToolDescriptor(
    val name: String,                                  // 模型用来调用的工具名
    val description: String,                           // 工具是干嘛的、何时用（模型看到的说明）
    val requiredParameters: List<ToolParameterDescriptor> = emptyList(),
    val optionalParameters: List<ToolParameterDescriptor> = emptyList(),
    val cacheControl: CacheControl? = null,
)
```

**`ToolParameterDescriptor(name, description, type)`** —— 注意参数名强制 **snake_case**（源码注释明确：`parameters are deserialized using CamelCase to snake_case conversion, so use snake_case names`）。

**`ToolParameterType`** 支持的类型：

| 类型 | 说明 |
|---|---|
| `String` / `Integer` / `Float` / `Boolean` / `Null` | 基础类型 |
| `Enum(entries)` | 枚举取值 |
| `List(itemsType)` | 数组 |
| `Object(properties, requiredProperties, additionalProperties, additionalPropertiesType)` | 嵌套对象 |
| `AnyOf(types)` | 联合类型（含 null 的 anyOf 会自动转成 `type: ["x","null"]` 兼容部分厂商） |

### 1.3 结果如何回传（encodeResultToString）

工具执行成功后，Koog 用 `tool.encodeResultToStringUnsafe(result, serializer)` 生成**给 LLM 看的工具结果文本**（默认是 JSON 序列化结果）。可以在 `ToolBase.encodeResultToString` 上 override 成自然语言，让模型更容易理解。

## 二、如何把工具给 Koog

### 2.1 用 ToolRegistry 收集工具

```kotlin
val registry = ToolRegistry {          // ToolRegistryBuilder DSL
    tool(DatabaseQueryTool(db))        // 工具名必须唯一，重名抛异常
    tool(ReadFileTool(fs))
    // tools(listOf(...))              // 批量
}
// 或：registry.add(tool) / registry.addAll(...) / registry1 + registry2（按 name 去重合并）
// 查询：registry.getTool("db_query") / getTool<MyTool>() / getToolOrNull(...)
```

### 2.2 装配给 AIAgent（builder）

Koog 的 builder 基类 `AIAgentServiceBuilderBase` 提供公开 API：

```kotlin
public fun toolRegistry(toolRegistry: ToolRegistry): Self
```

三种 builder（`AIAgent.builder()` 派生的）都可用：
- `GraphAgentBuilder`（`graphStrategy(strategy)`）—— 自绘流程，推荐
- `FunctionalAgentBuilder`（`functionalStrategy(strategy)`）—— 循环式
- `PlannerAgentBuilder`（`plannerStrategy(strategy)`）

装配示例：

```kotlin
val agent = AIAgent.builder()
    .promptExecutor(executor)
    .agentConfig(agentConfig)
    .toolRegistry(registry)                    // ← 装配工具
    .install(ChatMemory.Feature) { config ->
        config.chatHistoryProvider = ...
    }
    .build()
```

### 2.3 工具如何流转到 LLM

```
ToolRegistry(ToolBase 实例)
   │ 执行时
   ▼
List<ToolDescriptor>   // 每个 Tool 的 descriptor（AIAgentLLMContext.tools）
   │  requestLLM() → executor.executeProcessed(prompt, model, tools)
   ▼
LLMClient.execute(prompt, model, tools)   // Mederi 的 MederiOpenAILLMClient.execute 第三个参数就是它
   │  OpenAICompatibleToolDescriptorSchemaGenerator
   ▼
OpenAI 兼容 tools JSON（含 name/description/parameters 的 type/properties/required）
   │ 发请求
   ▼
LLM 返回 tool_call → Koog 解析 → registry.getTool(name) → 执行 → 结果 encodeResultToString
```

注意：`AIAgentLLMContext` 里 `tools` 与 `toolRegistry` 是两个东西——`tools` 是发给 LLM 的 descriptor 列表；`toolRegistry` 是执行时按 name 找实例的注册表。二者由 builder 的 `.toolRegistry()` 同时建立。

## 三、如何把工具使用方式的提示词给 Koog

**核心结论：不写进 system prompt，全写在工具的 description 字段，以结构化 tools 参数传给 LLM。**

Koog 的 `OpenAICompatibleToolDescriptorSchemaGenerator`（[源码](../../../../Users/liuzhe/.gradle/caches/modules-2/files-2.1/ai.koog/koog-agents-jvm/1.1.1/b6ce82fb20bb3c9c0ae6bde82d005ec226e91b74/koog-agents-jvm-1.1.1-sources.jar) → `OpenAICompatibleToolDescriptorSchemaGenerator.kt`）把每个 `ToolDescriptor` 生成：

```json
{
  "type": "object",
  "properties": {
    "query": { "description": "<参数说明>", "type": "string" }
  },
  "required": ["query"]
}
```

再组装进 tools 数组（`{"type":"function","function":{"name","description","parameters"}}`）。**模型看到的工具使用方式 = name + description + 参数 description**。

所以写工具时的关键：
- `description` 要写清「工具是干什么的、什么场景用、怎么用、注意事项」——这就是给模型的工具使用提示词。
- 每个参数 `description` 写清含义、取值范围、格式。
- 工具结果通过 override `encodeResultToString` 输出对模型友好的文本。

### 补充：Koog 还有个「缺失工具转换」机制

`MissingToolsConversionStrategy`（`config.missingToolsConversionStrategy`）处理「历史里有工具调用、但本次请求没带该工具定义」的情况——比如子图切换后工具集不同。默认会把缺失的工具调用/结果转成**纯文本描述**（`ToolCallDescriber.describeToolCall/describeToolResult`）再发给模型，避免历史出现"引用未定义工具"导致 API 报错。子图/多阶段场景需注意配置。

## 四、Koog 到底有没有内置提示词

### 4.1 结论：agent 循环零内置 system prompt

逐一核实源码：
- `singleRunStrategy`（AIAgentSimpleStrategies.kt，Mederi AgentRunner 默认）：节点只有 `nodeLLMRequest → nodeExecuteTools → nodeLLMSendToolResults`，**无任何 system 注入**。
- `reActStrategy`（AIAgentStrategies.kt）：只追加 user 消息（`reasoningPrompt = "Please give your thoughts about the task and plan the next steps."`），**无 system 注入**。
- `chatAgentStrategy`：唯一注入是一个 user 反馈 `"Don't chat with plain text! Call one of the available tools, instead: <names>"`（当 LLM 返回纯文本时）。
- `AIAgentConfig` 的 `prompt` 默认 `Prompt.Empty`。

**系统提示词（人设、行为规范、工具总览引导）完全由我们通过 `Prompt.builder().system(systemPrompt)` 创建**——这正是 AgentRunner 里 `Prompt.builder(id = sessionId).system(systemPrompt)` 的职责，Koog 不兜底。

### 4.2 非 system prompt 的内置注入（注意，不是我们控制的）

| 注入点 | 内容 | 触发条件 |
|---|---|---|
| ChatMemory feature | `"Here are the relevant facts from memory: ..."` / `"Memory feature is not enabled"` | 启用 `ChatMemory.Feature` 时（Mederi 已启用） |
| chat 策略反馈 | `"Don't chat with plain text! Call one of the available tools, instead: ..."` | chatAgentStrategy，LLM 返回纯文本 |
| 工具失败文本 | `"Tool with name 'X' failed to parse/execute ... : <error>"` | 工具解析/执行抛异常（GenericAgentEnvironment 自动生成） |
| 工具结果文本 | `encodeResultToString` 输出 | 每次工具执行成功 |

这些是**功能性内置**，不是"系统提示词"，且大多可被我们的行为影响（比如工具抛 `ToolException` 时错误文本就是 `e.message`，可以用它向模型传达期望信息）。

### 4.3 对 Mederi 的意义

- **system prompt 完全自建**：`Agent.systemPrompt` 就是全部人设来源。要引导 agent 的工具使用习惯（先规划、再逐文件编辑等），写进 systemPrompt 即可。
- **工具说明不依赖 system prompt**：工具的「何时用、怎么用」写在 `ToolDescriptor.description`，自动结构化传给 LLM，**不需要**手写进 systemPrompt（写进去反而冗余浪费 token）。
- systemPrompt 里可放：通用行为规范 + 工具使用的宏观策略；工具级说明放 description。

## 五、Mederi 现状与改造建议

### 5.1 现状

`AgentRunner.kt`（[`infrastructure/koog/AgentRunner.kt`](../../mederi/core/src/main/kotlin/xyz/mederi/infrastructure/koog/AgentRunner.kt)）当前：
- 只装配 `promptExecutor + agentConfig + ChatMemory.Feature`，**未调用 `.toolRegistry()`**——即 agent 目前是纯文本的，不会调用任何工具。
- system prompt 来自 `agent.systemPrompt`。

### 5.2 加工具的步骤（改动很小）

1. **写工具类**：继承 `SimpleTool<Args, String>`，构造传 `name`/`description`（用 snake_case 参数名）。
2. **建 registry**：`ToolRegistry { tool(MyTool(...)) ... }`。
3. **装配**：在 `AIAgent.builder()` 链上加 `.toolRegistry(registry)`。
4. **可选**：override `encodeResultToString` 定制结果文本；`ToolException` 携带面向模型的错误信息。

### 5.3 关键注意点

- 工具名唯一（registry 内重名抛异常）。
- 参数名 snake_case（Koog 反序列化约定）。
- 子图/多阶段切换工具集时注意 `MissingToolsConversionStrategy`（默认行为会把缺失工具转成文本描述，Mederi 单策略场景暂不涉及）。
- `MederiOpenAILLMClient.execute(prompt, model, tools)` 的 `tools` 参数就是 Koog 传入的 `List<ToolDescriptor>`，Mederi 侧需确保客户端把 descriptor 正确序列化进请求体（含 name/description/parameters）——这与 vLLM 清洗工作是配套的。
