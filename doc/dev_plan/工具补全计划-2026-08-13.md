# 工具补全计划

> 创建日期：2026-08-13
> 状态：计划中
> 背景：Mederi 要具备"自己更新自己"的能力，需要给 agent 注册工具。Koog 的 `agents-ext` 模块提供了 6 个基础工具，但对照 Codex（OpenAI 的 coding agent）的工具集，还缺若干关键工具。

## 一、apply_patch vs EditFileTool：是否需要 apply_patch

### 1.1 两者格式对比

**Koog EditFileTool（搜索替换）**

```
Args(path, original, replacement)
```
一次调用只改一个位置：在文件里找 `original` 字符串，替换成 `replacement`。
模糊匹配：处理 case 和 whitespace 不一致。

**Codex apply_patch（patch 格式）**

```
*** Begin Patch
*** Add File: path/to/new.kt
+val x = 1
+val y = 2
*** Update File: path/to/existing.kt
@@ class Foo {
-    val old = 1
+    val new = 2
@@
*** Delete File: path/to/old.kt
*** End Patch
```
一次调用可以：新增文件、删除文件、修改多个文件的多个位置。

### 1.2 apply_patch 强大在哪

| 维度 | EditFileTool | apply_patch |
|---|---|---|
| 单次改多个文件 | ❌ 不行，一次一个文件 | ✅ 一个 patch 里包含多个文件的改动 |
| 单次改多个位置 | ❌ 不行，一次一个 original/replacement | ✅ 一个文件里可以有多个 @@ 上下文块，每块独立改 |
| 新增文件 | 需要另外的 WriteFileTool | ✅ `*** Add File` 一次搞定 |
| 删除文件 | ❌ 没有 | ✅ `*** Delete File` |
| 移动/重命名文件 | ❌ 没有 | ✅ `*** Move to` |
| 模糊匹配 | case + whitespace | 4 级递进：精确 → 去尾空格 → 双向 trim → Unicode 标点归一化 |
| 原子性 | 单次单处，改一半失败留下中间状态 | 整个 patch 要么全成功要么全失败（有 committed_delta 回滚） |
| token 效率 | 每次都要传完整 original + replacement | 只传 diff 行（`+`/`-`），上下文行用 ` ` 前缀，省 token |

### 1.3 模糊匹配的 4 级递进（seek_sequence）

Codex 的 `seek_sequence` 函数按以下顺序尝试匹配，逐级放宽：

1. **精确匹配**：`lines[i..] == pattern`，逐字节相等
2. **去尾空格**：`lines[i].trim_end() == pat.trim_end()`，忽略行尾空格差异
3. **双向 trim**：`lines[i].trim() == pat.trim()`，忽略行首行尾空格差异
4. **Unicode 归一化**：把智能引号（`""''`）、各种破折号（`—–-`）、特殊空格（`\u00A0` 等）归一化成 ASCII 后再 trim 比较

Koog 的 EditFileTool 只有第 1-2 级（case + whitespace）。

### 1.4 结论：需要，但不是第一优先级

apply_patch 在以下场景明显更强：
- **大范围重构**（一次改多个文件、多处）——EditFileTool 要调很多次，apply_patch 一次搞定
- **新增 + 修改 + 删除混合操作**——EditFileTool 要配合 WriteFileTool 调三次
- **LLM 生成的 patch 容错**——4 级模糊匹配比 2 级更能容忍 LLM 的细微格式偏差
- **token 效率**——大改时只传 diff 行，不传完整 original，省大量 token

**结论：已纳入实现计划，优先级为所有工具中最低（2026-08-13 确认）。**

- 不是「以后再说」，而是**确定要做的实现项，只是排在所有工具的最后一位**：先让 agent 用 `EditFileTool` + `WriteFileTool` 跑通 agent loop，再实现其它补充工具，最后才轮到 apply_patch。
- 不替换 `EditFileTool`，而是**补充**它：`EditFileTool` 保留用于单文件单段的简单替换，`apply_patch` 用于多文件/多 chunk 的大改动、Add/Delete/Move/EOF 追加组合操作。
- 实现复杂度中等（见下），解析器 + 模糊匹配边界多，所以排最末。
- 详细实现方案已写入 [apply_patch 开发文档](tools/apply_patch.md)（含与 EditFileTool 的对比、四阶段解析流程、Kotlin 实现建议）。

## 二、需要补的工具清单

按优先级分三档。第一优先级是 agent 能正常跑、能自我管理；第二优先级是多 agent 协作；第三优先级是锦上添花。

### 第一优先级：核心能力（建议首批实现）

#### 1. update_plan（计划管理）

- **Codex 对应**：`update_plan` 工具，维护步骤列表（step + status: pending/in_progress/completed）
- **TRAE 对应**：`TodoWrite`
- **Koog 有没有**：❌ 没有
- **为什么需要**：agent 不带计划容易跑偏，尤其多步骤任务（改代码 → 编译 → 修错 → 再编译）。计划让 agent 自己跟踪进度，也让用户看到进展。
- **实现复杂度**：低。一个 `UpdatePlanTool`，args 是 `plan: List<{step, status}>`，存储在 agent session 的 context 里。不涉及 IO，纯内存状态。
- **实现方式**：自己实现，继承 Koog 的 `Tool<Args, Result>`。

#### 2. get_context_remaining（上下文余量查询）

- **Codex 对应**：`get_context_remaining` 工具，返回 `tokens_left: Int`
- **TRAE 对应**：❌ 没有（TRAE 的上下文管理是隐式的）
- **Koog 有没有**：❌ 没有
- **为什么需要**：长任务跑到一半上下文满了会崩。agent 需要知道还剩多少 token，决定是否该压缩历史或收尾。Codex 在实战中发现这很关键——没有它 agent 会盲目继续直到 OOM。
- **实现复杂度**：中。需要知道模型的 context window 大小（`LLModel.contextLength`），需要统计当前 Prompt 的 token 数（需要 tokenizer）。
- **实现方式**：自己实现。token 统计可以用 Koog 的 `agents-features-tokenizer`（如果引入），或粗略按字符数估算（1 token ≈ 4 字符）。

#### 3. new_context_window（开新上下文窗口）

- **Codex 对应**：`new_context_window` 工具
- **TRAE 对应**：❌ 没有
- **Koog 有没有**：❌ 没有
- **为什么需要**：当 `get_context_remaining` 返回余量不足时，agent 可以开新上下文窗口——保留关键信息（计划、最近改动），丢弃旧对话，继续工作。这是长任务不崩的关键机制。
- **实现复杂度**：中。需要 Koog 的历史压缩能力（`nodeLLMCompressHistory`），或自己实现"保留最近 N 条 + 计划摘要"的截断逻辑。
- **实现方式**：自己实现。结合 HistoryStore 的 `replace` 方法（全量替换历史）。

### 第二优先级：多 Agent 协作（后续实现）

#### 4. spawn_agent（启动子 agent）

- **Codex 对应**：`spawn_agent`（v1/v2 都有）
- **TRAE 对应**：`Task`（启动子 agent）
- **Koog 有没有**：有 subgraph 机制（策略图里调子图），但没有"运行时动态启动子 agent"的工具
- **为什么需要**：复杂任务拆分——主 agent 负责规划，子 agent 并行处理不同文件/模块。
- **实现复杂度**：高。需要管理子 agent 的生命周期、消息传递、结果汇总。

#### 5. send_message / followup_task（给子 agent 发消息/追加任务）

- **Codex 对应**：`send_message`、`followup_task`
- **为什么需要**：子 agent 启动后，主 agent 可能要给它补充信息或追加子任务。
- **实现复杂度**：中。需要子 agent 的消息队列。

#### 6. wait_agent（等待子 agent 完成）

- **Codex 对应**：`wait_agent`，带超时参数
- **为什么需要**：主 agent 启动子 agent 后，需要等它完成拿结果。
- **实现复杂度**：低。等子 agent 的输出 Flow 完成。

#### 7. interrupt_agent（中断子 agent）

- **Codex 对应**：`interrupt_agent`
- **为什么需要**：子 agent 跑偏了或超时了，主 agent 可以中断它。
- **实现复杂度**：低。取消子 agent 的协程。

#### 8. list_agents（列出活跃子 agent）

- **Codex 对应**：`list_agents`
- **为什么需要**：主 agent 需要知道当前有哪些子 agent 在跑。
- **实现复杂度**：低。返回活跃子 agent 列表。

### 第三优先级：辅助工具（按需实现）

#### 9. write_stdin（向运行中命令写输入）

- **Codex 对应**：`write_stdin`，向 `exec_command` 返回的 session 写输入
- **为什么需要**：交互式命令（如 `./gradlew run` 启动后要输入参数、或 CLI 提示确认时自动回答）。
- **实现复杂度**：高。需要管理长期运行的命令 session，Koog 的 `ExecuteShellCommandTool` 是同步的（等命令结束返回），不支持中途写 stdin。
- **是否需要**：暂不需要。coding agent 主要跑短命令（编译/测试），很少需要交互式 stdin。

#### 10. tool_search（搜索延迟加载的工具）

- **Codex 对应**：`tool_search`，搜索按需加载的工具
- **为什么需要**：工具太多时全部塞给 LLM 会浪费 token。Codex 把部分工具标记为 deferred，agent 用 `tool_search` 按需发现。
- **实现复杂度**：中。
- **是否需要**：暂不需要。Mederi 当前工具数量少（十几个），全部直接给 LLM 没问题。等工具超过 20 个再考虑。

#### 11. view_image（查看图片）

- **Codex 对应**：`view_image`
- **为什么需要**：看 UI 截图、设计图、图表。
- **实现复杂度**：中。需要把图片转成 LLM 能接收的格式（vision 模型支持）。
- **是否需要**：暂不需要。纯 coding agent 不需要看图。如果做 UI 开发 agent 再加。

#### 12. current_time（获取当前时间）

- **Codex 对应**：`current_time`
- **为什么需要**：agent 需要时间感知（判断文件修改时间、日志时间戳、生成日期）。
- **实现复杂度**：极低。返回 `Instant.now()`。
- **是否需要**：可选。简单到可以随时加。

#### 13. wait_for_environment（等待环境就绪）

- **Codex 对应**：`wait_for_environment`
- **为什么需要**：等 Docker 容器/远程环境启动完成。
- **实现复杂度**：中。
- **是否需要**：暂不需要。Mederi 本地开发不需要等环境。

## 三、实现路径建议

### 阶段一：让 agent 能跑（现在）

1. 引入 `koog-agents-ext` 依赖

6. 实现 `get_context_remaining`（上下文余量）
7. 实现 `new_context_window`（开新上下文）

8. 实现 `spawn_agent` + `send_message` + `wait_agent` + `interrupt_agent` + `list_agents`

### apply_patch 实现记录（2026-08-15）

**实现文件**：
- `core/src/main/kotlin/xyz/mederi/tools/patch/PatchParser.kt`——数据模型（`PatchHunk`/`UpdateChunk`）+ 逐行状态机解析器（带行号报错，heredoc lenient 兼容）
- `core/src/main/kotlin/xyz/mederi/tools/patch/PatchApplier.kt`——`seekSequence` 四级模糊匹配（精确 → trimEnd → trim → Unicode 标点归一化）+ `computeReplacements` 游标顺序定位 + `deriveNewContents`
- `core/src/main/kotlin/xyz/mederi/tools/FileSystemTools.kt`——`ApplyPatchTool`（三阶段：解析 → dry-run 验证（磁盘零改动）→ 原子应用，git 风格 A/M/D 摘要）
- `core/src/main/kotlin/xyz/mederi/tools/ToolFactory.kt`——注册为 `apply_patch`，仅 EXECUTE 模式（EXPLORE/PLAN 排除）

**关键决策**：不用 true freeform（Koog 的 `Tool` 抽象只有 JSON-schema 函数调用，且 OPENAI_CHAT / OPENAI_RESPONSES / GOOGLE 三种 Provider 在 Koog 层统一走 JSON function calling），patch 以单字符串参数 `patch: String` 承载，格式说明写入 `@LLMDescription`。

**测试**（71 个用例，全部通过；core + server 全量回归通过）：
- `PatchParserTest`（24 个）：解析正确性 + 带行号错误信息，对齐 Codex parser/streaming_parser 用例
- `PatchApplierTest`（24 个）：四级匹配逐级验证、游标顺序推进、EOF 追加、哨兵截断重试、上下文/oldLines 找不到报错
- `ApplyPatchToolTest`（23 个）：**全部 `tool.execute()` 直接编辑临时目录真实文件并逐字断言结果**——Add/Update/Delete/Move 混合、多 chunk 非相邻修改、@@ 上下文定位、模糊匹配容忍空白差异、EOF 追加、验证失败磁盘零改动（原子性）、路径越界拒绝（含 move 目标）、重复路径报错、ToolFactory 注册验证

**初版裁剪（延后项）**：`environment_id` 多环境、`PreserveLineEndings` 混合行尾、流式解析进度事件、unified_diff 产物、审批/delta 回传。
