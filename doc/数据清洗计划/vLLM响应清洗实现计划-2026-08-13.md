## 一、要解决的核心问题：流式 reasoning 丢失

**agent 实际用的是流式路径**（coding agent 逐字输出代码和推理）。流式是核心，非流式是次要的。

### 流式问题（核心）

Koog 的流式链路（`OpenAILLMClient` 源码确认）：

```
httpClient.sse(...)                                    ← HTTP 层（Koog 原版，不动）
  → decodeStreamingResponse(rawJson: String)            ← 解析层（可 override）
      → OpenAIChatCompletionStreamResponse
          → choices[].delta: OpenAIStreamDelta          ← 只有 4 字段：content/refusal/role/toolCalls
  → processStreamingResponse(Flow<...StreamResponse>)   ← 转换层（可 override）
      → 只调 emitTextDelta / emitToolCallDelta          ← 不调 emitReasoningDelta
      → Flow<StreamFrame>
```

**问题**：
1. `OpenAIStreamDelta` 没有 `reasoningContent` 字段 → Hetzner 的 `delta.reasoning` 被 `ignoreUnknownKeys` 丢弃
2. `processStreamingResponse` 不调 `emitReasoningDelta` → 即使有 reasoning 数据也没出口

**Koog 流式基础设施完全就绪**（源码确认）：
- `StreamFrame.ReasoningDelta` 存在（`StreamFrame.kt` 第 60 行）
- `StreamFrameFlowBuilder.emitReasoningDelta` 存在（`StreamFrameFlowBuilder.kt` 第 159 行），自动累积 pending reasoning，`emitEnd` 时输出 `ReasoningComplete`
- Responses API 路径已在用 `emitReasoningDelta`（`OpenAILLMClient.kt` 第 383 行）

**就是 Chat Completions 流式路径没接上**。我们要 override `decodeStreamingResponse` + `processStreamingResponse` 把它接上。

### 非流式问题（次要）

Koog 的 `OpenAIMessage.Assistant` 有 `reasoningContent` 字段，基类 `processProviderChatResponse` 已支持 `reasoningContent` → `MessagePart.Reasoning`。只需 override `decodeResponse` 让 `reasoning` 字段被解析。

## 二、设计原则

### 2.1 按需清洗，非清洗直通

标准供应商直通 Koog 原版 client，零开销。`Provider` 加 `responseSanitization: Boolean = false` 标记，`KoogClientFactory` 按标记分派。

### 2.2 兜底兼容

优先读标准字段 `reasoning_content`，缺失才读非标准 `reasoning` 兜底。供应商修好了自动适配。

### 2.3 每家一个独立函数

需要清洗的供应商少，每家一个独立函数（如 `sanitizeHetznerResponse`），不搞接口/策略模式。

## 三、MederiOpenAILLMClient 设计

### 3.1 实现关系

```
LLMClient (Koog 抽象类)
  └─ MederiOpenAILLMClient (Mederi 清洗版，直接继承 LLMClient)
       ├─ 网络层：Koog 的 KoogHttpClient（复用，不自己写 HTTP）
       └─ 解析层：自己的 Sanitized 模型 + buildStreamFrameFlow
```

不继承 Koog 的 `OpenAILLMClient`（其请求序列化大量 internal 依赖，override 受限）。
直接继承 `LLMClient`，自己拼请求 JSON + 解析响应，网络请求复用 Koog 的 `KoogHttpClient`。

### 3.2 实现的方法

| 方法 | 作用 | 实现 |
|---|---|---|
| `execute(prompt, model, tools)` | 非流式 | 拼请求 JSON → `httpClient.post` → 解析 SanitizedChatCompletionResponse → 构造 Message.Assistant（含 MessagePart.Reasoning） |
| `executeStreaming(prompt, model, tools)` | 流式（核心） | 拼请求 JSON → `httpClient.sse` → 解析 SanitizedStreamResponse → `buildStreamFrameFlow` 调 `emitReasoningDelta` |
| `models()` | 列模型 | 返回空列表（vLLM 端点不一定支持） |
| `moderate()` | 内容审核 | 抛 UnsupportedOperationException |
| `llmProvider()` | 供应商 | 返回 LLMProvider.OpenAI |
| `close()` | 关闭 | 委托 httpClient.close() |

### 3.3 自定义流式数据模型（关键）

Koog 的 `OpenAIStreamDelta` 没有 reasoning 字段，不能用。自定义一个：

```kotlin
@Serializable
data class SanitizedStreamDelta(
    val content: String? = null,
    val reasoningContent: String? = null,           // 标准：JSON "reasoning_content"
    @SerialName("reasoning") val reasoningAlias: String? = null,  // 兜底：JSON "reasoning"
    val role: String? = null,
    val toolCalls: List<OpenAIStreamToolCall>? = null
) {
    val effectiveReasoning: String? get() = reasoningContent ?: reasoningAlias
}
```

`executeStreaming` 内部用这个模型解析 SSE chunk → `processStreamingFlow` 读 `delta.effectiveReasoning` → 调 `emitReasoningDelta`。

### 3.4 processStreamingFlow 实现（核心）

```kotlin
private fun processStreamingFlow(response: Flow<SanitizedStreamResponse>): Flow<StreamFrame> =
    buildStreamFrameFlow {
        var finishReason: String? = null
        var metaInfo: ResponseMetaInfo? = null

        response.collect { chunk ->
            chunk.choices.firstOrNull()?.let { choice ->
                // 1. 文本增量
                choice.delta.content?.let { emitTextDelta(it, choice.index) }

                // 2. reasoning 增量——这是核心，Koog 原版 OpenAILLMClient 不调这行
                choice.delta.effectiveReasoning?.let { emitReasoningDelta(text = it, index = choice.index) }

                // 3. 工具调用增量
                choice.delta.toolCalls?.forEach { ... emitToolCallDelta(...) }

                choice.finishReason?.let { finishReason = it }
            }
            chunk.usage?.let { metaInfo = createMetaInfo(it) }
        }

        emitEnd(finishReason, metaInfo)
    }
```

`buildStreamFrameFlow` 的 `StreamFrameFlowBuilder` 会自动：累积 reasoning delta → 在 `emitEnd` 时输出 `ReasoningComplete`。我们只需调 `emitReasoningDelta`，生命周期管理 Koog 替我们做。

### 3.5 非流式数据模型

```kotlin
@Serializable
@SerialName("assistant")
data class SanitizedAssistantMessage(
    val content: String? = null,
    val reasoningContent: String? = null,
    @SerialName("reasoning") val reasoningAlias: String? = null,
    val toolCalls: List<OpenAIToolCall>? = null,
    val refusal: String? = null
) {
    val effectiveReasoning: String? get() = reasoningContent ?: reasoningAlias
}
```

`decodeResponse` 用这个解析 → 把 `effectiveReasoning` 填入 Koog `OpenAIMessage.Assistant.reasoningContent` → 基类 `processProviderChatResponse` 自动转 `MessagePart.Reasoning`。

### 3.6 清洗函数

每家供应商一个独立纯函数，兜底式：

```kotlin
fun sanitizeHetznerResponse(rawJson: String): String {
    // 解析为 JsonObject
    // message/delta 有 "reasoning" 且无 "reasoning_content" → 补 "reasoning_content"
    // 已有 "reasoning_content" → 不动
    // 返回修改后的 JSON
}
```

> 注：如果用自定义模型的双字段兼容（3.3/3.5），清洗函数可以不做 JSON 重写——模型层已兜底。清洗函数保留作为可选手段，处理模型层覆盖不了的特殊情况。

## 四、实现步骤

### Step 0：Provider 加标记

- `Provider` 加 `responseSanitization: Boolean = false`
- `CreateProviderRequest` 加字段，`ProviderApiImpl.create` 传递
- 序列化测试

### Step 1：自定义流式数据模型（核心）

- 新建 `xyz.mederi.provider.infrastructure.koog.sanitize` 包
- 写 `SanitizedStreamDelta`（双字段 + `effectiveReasoning`）
- 写 `SanitizedStreamResponse` / `SanitizedStreamChoice`（包装 SanitizedStreamDelta）
- 写 `SanitizedAssistantMessage`（非流式，双字段 + `effectiveReasoning`）
- 写 `SanitizedChatCompletionResponse` / `SanitizedChoice`（非流式包装）
- 配套 Json 实例（SnakeCase + ignoreUnknownKeys）
- 单元测试：
  - Hetzner 真实流式 JSON（`"reasoning"`）→ `effectiveReasoning` 有值
  - 标准 JSON（`"reasoning_content"`）→ `effectiveReasoning` 有值（标准优先）
  - 两个都没有 → null

### Step 2：MederiOpenAILLMClient（以流式 reasoning 为核心）

- 继承 `LLMClient`，构造接收 `KoogHttpClient`（由 KoogClientFactory 用 `AbstractOpenAILLMClient.createConfiguredHttpClient` 创建）
- 实现 `executeStreaming`：`httpClient.sse` → 解析 `SanitizedStreamResponse` → `processStreamingFlow` 调 `emitReasoningDelta(effectiveReasoning)`——这是解决流式问题的核心
- 实现 `execute`：`httpClient.post` → 解析 `SanitizedChatCompletionResponse` → 构造 `Message.Assistant`（含 `MessagePart.Reasoning`）
- 实现请求 JSON 构建（`buildChatRequestJson` / `buildMessageJson` / `buildToolJson`）
- 单元测试：用真实 Hetzner JSON mock，验证 `StreamFrame.ReasoningDelta` 被输出

### Step 3：KoogClientFactory 按需分派

- `responseSanitization = false` → Koog 原版 `OpenAILLMClient`
- `responseSanitization = true` → `MederiOpenAILLMClient`
- 测试

### Step 4：AgentRunner 适配

- 类型兼容（继承链），确认 `as LLMClient` 正确，大概率零改动

### Step 5：端到端验证

- Hetzner Provider（`responseSanitization = true`）流式对话 → reasoning 以 `StreamFrame.ReasoningDelta` 输出
- 标准 OpenAI Provider 行为不变
- 兜底兼容：模拟标准 `reasoning_content` 也能解析

## 五、不清洗的字段

| 字段 | 原因 |
|---|---|
| `content`/`role`/`refusal`/`finish_reason` | 字段名匹配 |
| `tool_calls` 全部子字段 | 字段名匹配 + id 不校验格式 |
| `usage` 全部子字段 | 字段名匹配 |
| vLLM 内部字段（9个） | Koog `ignoreUnknownKeys` 忽略 |
