# 供应商数据清洗调研

> 创建日期：2026-08-13
> 状态：调研中（逐 API 测试记录）
> 目的：记录各 OpenAI 兼容端点的字段偏差，明确标准字段 vs 实际字段，为后续清洗方案提供依据

---

## 调研方法

对每个 OpenAI 兼容端点，逐 API（models / chat/completions / ...）用 curl 实测，记录：
1. **标准字段**：OpenAI 官方 API 该返回什么字段
2. **实际字段**：该供应商实际返回了什么
3. **偏差**：多余字段 / 缺失字段 / 语义错位字段
4. **清洗需求**：哪些偏差需要 Mederi 纠正

## API 1：GET /v1/models（列出模型）

### 1.1 标准 OpenAI 响应

**来源**：OpenAI 官方 API Reference（https://platform.openai.com/docs/api-reference/models/list）

**顶层结构**：
```json
{
  "object": "list",
  "data": [ <model object>, ... ]
}
```

**标准 model object 字段**（仅 4 个）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 模型标识符，如 "gpt-4o" |
| `object` | string | 固定值 "model" |
| `created` | integer | Unix 时间戳（秒），模型创建时间 |
| `owned_by` | string | 模型所有者，如 "openai" / "organization-owner" |

**标准示例**（OpenAI 官方）：
```json
{
  "object": "list",
  "data": [
    {
      "id": "gpt-5.2",
      "object": "model",
      "created": 1686935002,
      "owned_by": "openai"
    }
  ]
}
```

> **注意**：标准 OpenAI model object **不含** 上下文长度、最大输出 token 等字段。OpenAI 的 `/v1/models` 只提供模型标识，不提供能力/容量信息。Koog 的 `LLModel` 有 `contextLength`/`maxOutputTokens` 字段，但 OpenAI 官方 models 接口本就不返回这些——这两者不矛盾，Koog 的这些字段靠预定义模型常量（`OpenAIModels.Chat.GPT4o`）填充，而非靠 models 接口解析。

### 1.3 Hetzner 偏差分析（models 接口）

#### 字段逐项对比

| 标准字段 | Hetzner 是否有 | 说明 |
|---|---|---|
| `id` | ✅ 有，格式标准 | 值如 "Qwen/Qwen3.6-35B-A3B-FP8"（带斜杠，OpenAI 标准允许） |
| `object` | ✅ 有，值为 "model" | 标准 |
| `created` | ✅ 有，Unix 秒时间戳 | 格式标准 |
| `owned_by` | ✅ 有，值为 "hetzner" | 格式标准 |

#### Hetzner 多出的非标准字段

| 多出字段 | 类型 | 值（示例） | 来源推断 | 对 Koog/Mederi 的影响 |
|---|---|---|---|---|
| `root` | string | `"/model"` | vLLM 内部字段（模型路径根） | 无害。Koog `ignoreUnknownKeys` 会忽略。但语义上不该出现在 API 响应 |
| `parent` | string\|null | `null` | vLLM 内部字段（父模型，用于 LoRA 衍生模型标识） | 无害。同上被忽略 |
| `max_model_len` | integer | `262144` / `512000` | **vLLM 字段**（transformers/vLLM 风格，非 OpenAI 标准） | **有价值但字段名不标准**。OpenAI 标准无此字段；若要保留上下文长度，需映射到 Koog `LLModel.contextLength` |

#### Hetzner 缺失的标准字段

无。4 个标准字段都齐全。

#### 语义错位字段

无。models 接口的字段语义没有错位（不像 chat/completions 那样把内容塞错位置）。

### 1.4 models 接口清洗需求

| 偏差 | 是否需要清洗 | 清洗方式 | 优先级 |
|---|---|---|---|
| `root`/`parent` 多余字段 | ❌ 不需要 | Koog `ignoreUnknownKeys=true` 自动忽略 | - |
| `max_model_len` 非标准字段名 | ⚠️ 视需求 | 若 Mederi 要展示模型上下文长度，需在解析 models 响应时把 `max_model_len` 映射到 `LLModel.contextLength`。但 Koog 的 `OpenAILLMClient.models()` 按标准解析，不会读这个字段——信息会丢 | 低（不影响核心对话功能，仅影响元信息展示） |

**结论**：models 接口**不需要强制清洗**。Hetzner 的偏差属于"多了 vLLM 内部字段"，不影响 Koog 解析 `id`（核心字段）。`max_model_len` 是有用的额外信息但非标准，是否保留取决于 Mederi 是否需要展示上下文长度——属于增强项，非阻断项。

## API 2：POST /v1/chat/completions（对话）

### 2.1 标准 OpenAI 响应

**顶层结构**：
```json
{
  "id": "chatcmpl-xxx",
  "object": "chat.completion",
  "created": 1686935002,
  "model": "gpt-4o",
  "choices": [ { <choice> } ],
  "service_tier": null,
  "system_fingerprint": "fp_xxx",
  "usage": { <usage> }
}
```

**标准 choice 字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `index` | integer | 选择索引，通常 0 |
| `message.role` | string | "assistant" |
| `message.content` | string\|null | 回复正文 |
| `message.refusal` | string\|null | 拒绝原因（OpenAI 扩展） |
| `message.annotations` | array\|null | 注解 |
| `message.audio` | object\|null | 音频回复 |
| `message.function_call` | object\|null | 已废弃，被 tool_calls 替代 |
| `message.tool_calls` | array\|null | 工具调用 |
| `logprobs` | object\|null | 对数概率 |
| `finish_reason` | string | "stop" / "length" / "tool_calls" / "content_filter" |

**标准 usage 字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `prompt_tokens` | integer | 输入 token 数 |
| `completion_tokens` | integer | 输出 token 数 |
| `total_tokens` | integer | 总 token 数 |
| `prompt_tokens_details` | object\|null | 输入 token 明细（cached_tokens 等） |
| `completion_tokens_details` | object\|null | 输出 token 明细 |

> **注意**：标准 OpenAI chat/completions 响应**没有** `reasoning` / `reasoning_content` 字段。OpenAI 的 reasoning 模型（o 系列）在 Chat Completions API 里不返回推理过程，推理过程仅在 Responses API 中通过 `reasoning` 字段返回。vLLM 自定义的 `reasoning` 字段是非标准扩展。

### 2.5 chat/completions 偏差分析

#### 关键发现 1：两个模型字段结构不一致

DeepSeek 比 Kimi 多了 `ec_transfer_params` 和 `metrics` 两个字段。说明 Hetzner 的 vLLM **按模型不同暴露不同内部字段**，非统一接口。同一个端点、同一个 API，换模型字段就变——这对客户端解析是隐患。

#### 关键发现 2：`stop_reason` 语义不一致

| 模型 | `stop_reason` 值 |
|---|---|
| Kimi | `163586`（vLLM 内部 token id） |
| DeepSeek | `null` |

同一个字段，一个模型返回数字一个返回 null。这是 vLLM 内部状态泄漏，不是 API 设计字段。标准 OpenAI 只有 `finish_reason`（"stop"/"length" 等），没有 `stop_reason`。

#### 关键发现 3：`reasoning` 字段（vLLM 非标准扩展）

两个 reasoning 模型都把推理过程放在 `message.reasoning`。这是 vLLM 的非标准扩展（OpenAI 标准的 reasoning 模型在 Chat Completions API 里不返回推理过程，仅在 Responses API 通过 `reasoning` 字段返回）。

**好消息**：`content` 同时有值——Koog 解析 `content` 不会丢内容，`reasoning` 被当作未知字段忽略。
**隐患**：如果 `max_tokens` 太小（如上次测试的 10），模型可能还在 reasoning 阶段就被截断，此时 `content` 为 null、内容全在 `reasoning` 里——Koog 会以为没有回复。

#### 关键发现 4：vLLM 内部字段一览（chat/completions）

以下字段均为 vLLM 推理引擎内部字段，不应出现在 OpenAI 兼容 API 响应中：

| 字段 | 位置 | 说明 |
|---|---|---|
| `prompt_logprobs` | 顶层 | prompt 的对数概率 |
| `prompt_token_ids` | 顶层 | prompt 的 token id 列表 |
| `prompt_text` | 顶层 | 原始 prompt 文本回显 |
| `kv_transfer_params` | 顶层 | 分布式 KV cache 传输参数 |
| `ec_transfer_params` | 顶层 | expert coordination 传输参数（仅部分模型） |
| `metrics` | 顶层 | 推理性能指标（仅部分模型） |
| `stop_reason` | choice | vLLM 内部停止原因（token id 或 null） |
| `token_ids` | choice | 输出 token id 列表 |
| `routed_experts` | choice | MoE 模型的专家路由信息 |
| `reasoning` | message | 推理过程文本（vLLM 扩展） |

### 2.6 chat/completions 清洗需求

| 偏差 | 是否需要清洗 | 清洗方式 | 优先级 |
|---|---|---|---|
| vLLM 内部字段（`prompt_logprobs`/`prompt_token_ids`/`prompt_text`/`kv_transfer_params`/`ec_transfer_params`/`metrics`/`token_ids`/`routed_experts`/`stop_reason`） | ❌ 不需要 | Koog `ignoreUnknownKeys=true` 自动忽略，不影响解析 | - |
| `reasoning` 字段（推理过程） | ⚠️ 视需求 | 若 Mederi 要展示推理过程，需保留。但 Koog 解析时可能丢弃——需确认 Koog 的 `OpenAILLMClient` 是否保留 `reasoning`。若丢弃，需自定义解析 | 中（影响 reasoning 展示功能） |
| `content` 为 null + 内容在 `reasoning`（max_tokens 不足时） | 🔴 **需要清洗** | 当 `content==null && reasoning!=null` 时，把 `reasoning` 内容回填到 `content`，否则 Koog 认为无回复 | **高**（影响核心对话正确性） |
| 两个模型字段不一致 | ❌ 不需要 | 多出的字段被忽略，缺失的标准字段（如 `tool_calls`）按 null 处理 | - |

**核心结论**：chat/completions 唯一需要强制清洗的是 **`content==null && reasoning!=null`** 的情况——这是语义错位，会导致 Koog 丢失回复内容。其余 vLLM 内部字段被 Koog 自动忽略，无害。

### 2.8 工具调用字段对比

#### 标准 OpenAI 工具调用响应

标准 OpenAI 工具调用时，`message` 结构：
```json
"message": {
    "role": "assistant",
    "content": null,
    "tool_calls": [
        {
            "id": "call_abc123def456",
            "type": "function",
            "function": {
                "name": "read_file",
                "arguments": "{\"path\": \"/etc/hostname\"}"
            }
        }
    ]
}
"finish_reason": "tool_calls"
```

#### 字段逐项对比

| 字段 | 标准 OpenAI | Kimi 实际 | 说明 |
|---|---|---|---|
| `message.tool_calls` | ✅ 数组 | ✅ 有 | **用了标准字段，未另搞字段** |
| `tool_calls[].id` | ✅ 如 `"call_abc123def456"` | ⚠️ `"functions.read_file:0"` | **格式非标准**（见下） |
| `tool_calls[].type` | ✅ "function" | ✅ "function" | 标准 |
| `tool_calls[].function.name` | ✅ | ✅ "read_file" | 标准 |
| `tool_calls[].function.arguments` | ✅ JSON 字符串 | ✅ `{"path": "/etc/hostname"}` | 标准 |
| `finish_reason` | ✅ "tool_calls" | ✅ "tool_calls" | 标准 |
| `message.content` | null（工具调用时） | null | 标准 |
| `message.reasoning` | ❌ 非标准 | 有值 | vLLM 扩展，工具调用前也有推理 |

#### `tool_calls[].id` 格式偏差

| 维度 | 标准 OpenAI | Kimi/vLLM |
|---|---|---|
| 格式 | `call_` 前缀 + 随机串 | `functions.<工具名>:<序号>` |
| 示例 | `call_abc123def456` | `functions.read_file:0` |
| 唯一性 | 全局随机 | 工具名+序号（同次调用内唯一） |

**影响**：id 仅用于关联工具调用与后续的工具结果消息（`role: "tool"` + `tool_call_id`），不限制格式。**通常无害**——除非上层代码对 id 做格式校验（如正则 `^call_`）。需确认 Koog 的 `OpenAILLMClient` 是否校验 id 格式。

### 2.9 工具调用清洗需求

| 偏差 | 是否需要清洗 | 清洗方式 | 优先级 |
|---|---|---|---|
| 工具调用用标准 `tool_calls` 字段 | ✅ 无偏差 | 无需清洗 | - |
| `tool_calls[].id` 格式非标准 | ⚠️ 视 Koog 实现 | 若 Koog 校验 id 格式，需规范化（如重写为 `call_` 前缀）。若不校验，无害 | 低（需确认 Koog 行为） |
| 工具调用时 `content` 为 null | ✅ 标准行为 | 无需清洗（`finish_reason: "tool_calls"` 明确区分，不同于 max_tokens 不足的 content==null） | - |
| `reasoning` 在工具调用时也有 | ⚠️ 同 2.6 | 若展示推理过程需保留 | 中 |

**结论**：工具调用链路**字段层面基本标准**——Kimi 用了 OpenAI 标准的 `tool_calls` 结构，Koog 应能正确解析。唯一需确认的是 `id` 格式是否被 Koog 校验。

### 2.10 KV 缓存与计费字段

#### 现象

两次对话测试中 `usage.prompt_tokens_details` 字段差异：

| 模型 | prompt_tokens | prompt_tokens_details | cached_tokens |
|---|---|---|---|
| Kimi | 104 | `null` | 未返回 |
| DeepSeek | 88 | `{"cached_tokens": 0, "multimodal_tokens": null}` | **0（未命中）** |

#### 字段来源

`cached_tokens` 是 vLLM 的 **prefix caching / automatic prefix caching** 功能暴露的字段，表示本次请求 prompt 命中 KV 缓存的 token 数。

- 标准 OpenAI 也有 `prompt_tokens_details.cached_tokens`，但语义是 OpenAI 服务端自己的 prompt 缓存
- Hetzner 这里返回的是 **vLLM 推理引擎的 KV cache 命中状态**，字段名恰好与 OpenAI 标准一致

#### 对计费的影响

1. **`prompt_tokens` 是实际计费的输入 token 总数**（无论是否命中缓存）
2. **`cached_tokens` 表示其中命中缓存的部分**——若 Hetzner 对缓存命中降价（类似 OpenAI 对 cached input 收半价），则：
   - 实际成本 = (prompt_tokens - cached_tokens) × 全价 + cached_tokens × 缓存价
   - 但 Hetzner 是否对缓存命中降价，API 响应无法判定，需查 Hetzner 计费文档
3. 当前测试 `cached_tokens: 0`，说明未命中缓存，全价计费

#### 对 Mederi 的影响

| 维度 | 影响 | 处理 |
|---|---|---|
| 计费准确性 | 若 Hetzner 缓存降价，Mederi 需读 `cached_tokens` 算真实成本 | 需确认 Koog 是否保留 `prompt_tokens_details.cached_tokens`（标准字段，可能保留） |
| 缓存命中优化 | vLLM prefix caching 按 prompt 前缀匹配；多轮对话中 system prompt + 早期历史不变，后续请求可能命中缓存，降延迟和成本 | Hetzner 的缓存是实例级，可能被其他用户挤掉，不可控 |
| `kv_transfer_params` | 顶层字段，vLLM 跨实例 KV cache 迁移参数 | 测试中为 null，说明 Hetzner 未启用跨实例迁移。无害（被 Koog 忽略） |

#### 清洗需求

`cached_tokens` 字段名与 OpenAI 标准一致，**无需清洗**——若 Koog 保留 `prompt_tokens_details`，Mederi 可直接读取用于成本计算。若 Koog 丢弃，需在自定义解析层保留。

#### 偏差确认

| 字段 | 值 | 说明 |
|---|---|---|

#### 清洗需求确认

这正是 2.6 节预测的 🔴 高优先级场景：**`content==null && reasoning!=null && finish_reason=="length"`**。

- Koog 的 `OpenAILLMClient` 解析 `content` 拿到 null，认为没有回复 → Mederi 丢失回复内容
- 实际内容在 `reasoning` 字段（vLLM 非标准扩展）
- **清洗规则**：当 `content==null && reasoning!=null` 时，把 `reasoning` 回填到 `content`，让 Koog 能解析到内容
- **注意区分**：工具调用时 `content==null` 是正常的（`finish_reason=="tool_calls"`），不应回填。只在 `finish_reason=="length"` 或 `"stop"` 且 `content==null && reasoning!=null` 时回填

#### 标准 OpenAI streaming 响应

标准 OpenAI streaming 用 `delta` 增量返回，`object` 为 `"chat.completion.chunk"`：
```

```

#### 字段对比

| 字段 | 标准 OpenAI streaming | Hetzner streaming | 说明 |
|---|---|---|---|
| `object` | "chat.completion.chunk" | "chat.completion.chunk" | 标准 |
| `choices[].delta.role` | 首个 chunk 有 | ✅ 首个 chunk 有 | 标准 |
| `choices[].delta.content` | 增量文本 | ⚠️ 仅首个 chunk 有空字符串 `""`，之后**无 content 增量** | **reasoning 模型把内容放 delta.reasoning** |
| `choices[].delta.reasoning` | ❌ 非标准 | ✅ 增量推理文本 | **vLLM 扩展，流式推理过程** |
| `choices[].delta.tool_calls` | 工具调用时增量 | 未测（推理被截断） | - |
| `choices[].finish_reason` | 最后 chunk 有 | ✅ "length"（最后 reasoning chunk） | 标准 |
| `choices[].token_ids` | ❌ 非标准 | null | vLLM 字段 |
| `choices[].stop_reason` | ❌ 非标准 | null | vLLM 字段 |
| 顶层 `prompt_token_ids` | ❌ 非标准 | null | vLLM 字段 |
| 顶层 `prompt_text` | ❌ 非标准 | null | vLLM 字段 |
| 末尾 usage chunk | ✅ 有 | ✅ 有（choices 为空数组） | 标准（OpenAI 需 stream_options.include_usage） |
| `data:[DONE]` | ✅ 结束标记 | ✅ 有 | 标准 |

#### 关键发现

1. **`delta.reasoning` 流式推理**：reasoning 模型在流式模式下，推理过程通过 `delta.reasoning` 增量返回（非标准字段）。标准 OpenAI streaming 的 `delta.content` 在推理阶段不返回内容。

2. **`content` 与 `reasoning` 的流式时序**：
   - 首个 chunk：`delta: {"role":"assistant","content":""}`（content 初始化为空）
   - 中间 chunks：`delta: {"reasoning":"..."}`（推理增量，**content 不出现**）
   - 若 max_tokens 足够：推理结束后会出现 `delta: {"content":"..."}`（正文增量）
   - 本次测试 max_tokens=20 太小，推理没结束就被截断（`finish_reason:"length"`），**content 始终没出现**

3. **流式清洗需求**：与 2.11 相同问题——若 max_tokens 不足导致只有 reasoning 没有 content，流式模式下 Koog 收到的 `delta.content` 全是空，最终拼接的 content 为空字符串。需要 Koog 在流式层也处理 `delta.reasoning`。

## 三、Hetzner 清洗需求总汇

### 需要清洗的（按优先级）

| 优先级 | 场景 | 偏差 | 清洗规则 | 影响范围 |
|---|---|---|---|---|
| 🔴 高 | 非流式对话，max_tokens 不足 | `content==null && reasoning!=null && finish_reason=="length"` | 把 `reasoning` 回填到 `content` | Koog 解析丢失回复 |
| 🔴 高 | 流式对话，max_tokens 不足 | `delta.content` 始终为空，内容在 `delta.reasoning` | 流式层处理 `delta.reasoning`，回填到 content | Koog 流式拼接丢失回复 |
| 🟡 中 | 非流式对话，reasoning 模型 | `reasoning` 字段（vLLM 推理过程） | 确认 Koog 是否保留；若丢弃且需展示，自定义解析 | 推理过程展示功能 |
| 🟡 中 | 计费 | `cached_tokens`（KV 缓存命中） | 确认 Koog 是否保留 `prompt_tokens_details` | 成本计算准确性 |
| 🟢 低 | 工具调用 | `tool_calls[].id` 格式 `functions.<name>:<n>` | 确认 Koog 是否校验 id 格式 | 工具调用关联 |

### 不需要清洗的

| 偏差 | 原因 |
|---|---|
| vLLM 内部字段（`prompt_logprobs`/`prompt_token_ids`/`prompt_text`/`kv_transfer_params`/`ec_transfer_params`/`metrics`/`token_ids`/`routed_experts`/`stop_reason`） | Koog `ignoreUnknownKeys=true` 自动忽略 |
| `max_model_len`（models 接口） | OpenAI 标准本无此字段，Koog 不读，信息丢失但不影响功能 |
| 两个模型字段不一致（`ec_transfer_params`/`metrics` 仅 DeepSeek 有） | 多出字段被忽略 |
| `/v1/models/{model}` 未实现 | 接口不存在，改用列表过滤 |
| `/v1/embeddings` 未实现 | 接口不存在 |
| `/v1/moderations` 未实现 | 接口不存在 |

### 清洗实现位置建议

| 清洗项 | 建议实现位置 | 理由 |
|---|---|---|
| `content==null && reasoning!=null` 回填 | **自定义 LLMClient 装饰器**（包住 OpenAILLMClient） | Koog 解析后 content 已是 null，需在解析层介入；装饰器模式与 RetryingLLMClient 一致 |
| `delta.reasoning` 流式回填 | 同上（装饰器 override executeStreaming） | 流式层同样问题 |
| `reasoning` 保留 | 确认 Koog 行为后定 | 若 Koog 保留则无需处理 |
| `cached_tokens` 保留 | 确认 Koog 行为后定 | 同上 |
| `tool_calls[].id` 格式 | 确认 Koog 行为后定 | 若不校验则无需处理 |

| `delta.reasoning` | 有 | 有 | 无此字段 | ⚠️ 保留（推理过程流式增量） |
| usage 位置 | 仅末尾 | **每 chunk（累积）** | 仅末尾（需 include_usage） | 取最后值（无害） |
| `delta.content` 时序 | 推理后出现 | 推理后出现 | 直接出现 | 无需处理（拼接逻辑不变） |

## 五、标准化方案

### 5.1 核心问题：字段名不匹配导致 Koog 无法正常解析

调研 Koog 源码（API 文档）确认了 Koog `OpenAILLMClient` 期望的 JSON 字段名。Hetzner 的字段名与 Koog 期望的不完全一致——**字段名不匹配的字段，Koog 读不到值，直接丢失**。

### 5.2 Koog 期望字段 vs Hetzner 实际字段（非流式 message）

Koog 的 `OpenAIMessage.Assistant` 类（`@Serializable`）定义的字段：

| Koog 字段（Kotlin） | Koog 期望的 JSON 字段名 | Hetzner 实际 JSON 字段名 | 匹配？ | 不匹配的后果 |
|---|---|---|---|---|
| `content` | `content` | `content` | ✅ | - |
| `reasoningContent` | `reasoningContent` | **`reasoning`** | ❌ **字段名差 "Content" 后缀** | **Koog 读到 null，推理内容丢失** |
| `toolCalls` | `toolCalls` | `tool_calls` | ⚠️ 见注 | Koog 通常用 `@SerialName("tool_calls")` 或宽松策略处理 snake_case |
| `toolCalls[].id` | `id`（String，不校验格式） | Kimi: `functions.x:0` / GLM: `chatcmpl-tool-xxx` | ✅ 格式不统一但类型匹配 | 无害（Koog 只当字符串用） |
| `toolCalls[].function.name` | `name` | `name` | ✅ | - |
| `toolCalls[].function.arguments` | `arguments` | `arguments` | ✅ | - |
| `refusal` | `refusal` | `refusal` | ✅ | - |
| `audio` | `audio` | `audio` | ✅ | - |
| `annotations` | `annotations` | `annotations` | ✅ | - |

> 注：Koog 的 Kotlin 属性名是 `toolCalls`（驼峰），OpenAI 标准 JSON 是 `tool_calls`（snake）。Koog 的 `OpenAILLMClient` 内部 Json 配置通常处理了这个转换（`explicitNulls=false` + 可能有 `@SerialName`）。Hetzner 返回 `tool_calls` 符合 OpenAI 标准，Koog 应能解析——需实测确认。

### 5.3 Koog 期望字段 vs Hetzner 实际字段（流式 delta）

Koog 的 `OpenAIStreamDelta` 类定义的字段：

| Koog 字段（Kotlin） | Koog 期望的 JSON 字段名 | Hetzner 实际 JSON 字段名 | 匹配？ | 不匹配的后果 |
|---|---|---|---|---|
| `content` | `content` | `content` | ✅ | - |
| `role` | `role` | `role` | ✅ | - |
| `refusal` | `refusal` | `refusal` | ✅ | - |
| `toolCalls` | `toolCalls` | `tool_calls` | ⚠️ 同上 | - |
| **（无 reasoningContent 字段）** | **无** | **`reasoning`** | ❌ **Koog 的 StreamDelta 根本没有 reasoning 字段** | **流式推理内容完全丢失，无法保留** |

**关键发现**：Koog 的 `OpenAIStreamDelta` 类**只有 4 个字段**（content/refusal/role/toolCalls），**没有 `reasoningContent`**。即使 Hetzner 返回 `delta.reasoning`，Koog 在流式模式下连解析字段都没有——`ignoreUnknownKeys` 直接丢弃。

### 5.4 字段名不匹配汇总

| 场景 | Hetzner 字段 | Koog 期望字段 | 影响 | 严重性 |
|---|---|---|---|---|
| 非流式 reasoning | `message.reasoning` | `message.reasoningContent` | 推理内容读不到（null） | 🔴 高（推理过程丢失） |
| 流式 reasoning | `delta.reasoning` | **Koog 无此字段** | 流式推理内容完全丢失 | 🔴 高（且无法在 Koog 层修复） |

### 5.5 标准化清洗规则

针对字段名不匹配，清洗规则是**在 HTTP 响应到达 Koog 解析层之前，把 Hetzner 的字段名重写成 Koog 期望的字段名**：

#### 非流式响应清洗

| 清洗动作 | 触发条件 | 实现 |
|---|---|---|
| `message.reasoning` → `message.reasoningContent` | 响应 JSON 中 `message` 有 `reasoning` 字段且无 `reasoningContent` | 拦截 HTTP 响应，JSON 字段名重写 |

#### 流式响应清洗

| 清洗动作 | 触发条件 | 实现 |
|---|---|---|
| `delta.reasoning` → `delta.reasoningContent` | 流式 chunk 的 `delta` 有 `reasoning` 字段 | 拦截 SSE chunk，JSON 字段名重写 |
| ⚠️ **但 Koog 的 `OpenAIStreamDelta` 没有 `reasoningContent` 字段** | 即使重写 Koog 也读不到 | 需在 Koog 之外保留（自定义流处理） |

#### 其他字段（无需清洗）

| 字段 | 状态 |
|---|---|
| `content` / `role` / `refusal` / `finish_reason` | ✅ 字段名匹配，无需清洗 |
| `tool_calls`（snake→驼峰） | ⚠️ 需确认 Koog 是否自动处理 snake_case |
| `tool_calls[].id`（格式不统一） | ✅ Koog 不校验格式，无需清洗 |
| vLLM 内部字段（`prompt_logprobs`/`token_ids` 等） | ✅ Koog `ignoreUnknownKeys` 忽略，无需清洗 |

### 5.6 标准化实现方案（已定稿）

曾考虑过三个方案，实测后均不可行，最终采用方案 D：

| 方案 | 不可行原因 |
|---|---|
| A. 自定义 LLMClient 装饰器 | `OpenAILLMClient.execute` 内部已完成 HTTP+解析，装饰器拿到的是已解析的 `Message.Assistant`——`reasoning` 已丢 |
| B. 自定义 HTTP 拦截（KoogHttpClient） | 非流式可行，但流式 `OpenAIStreamDelta` 硬缺 reasoning 字段，重写 JSON 字段名后 Koog 仍丢弃 |
| C. 继承 OpenAILLMClient override 解析 | `toOpenAIChatParams`/`OpenAIChatCompletionRequest` 是 internal、`settings` 是 private——继承路线处处碰壁 |

**最终方案 D：自己实现 LLMClient**（`MederiOpenAILLMClient`）：
- 直接继承 Koog 的 `LLMClient` 抽象类
- 网络层复用 Koog 的 `KoogHttpClient`（`AbstractOpenAILLMClient.createConfiguredHttpClient` 创建）
- 自己拼请求 JSON（`buildJsonObject`，无 internal 依赖）
- 自己解析响应（Sanitized 模型，双字段兼容）
- 流式 reasoning 直接 `emitReasoningDelta`（不受 `OpenAIStreamDelta` 限制）

详见 [vLLM响应清洗实现计划](vLLM响应清洗实现计划-2026-08-13.md)。

### 5.7 清洗需求最终定级

| 优先级 | 清洗项 | 原因 | 实现方案 |
|---|---|---|---|
| 🔴 高 | 非流式 `message.reasoning` | 字段名不匹配，Koog 读不到推理内容 | 方案 D：MederiOpenAILLMClient 用 Sanitized 模型解析 |
| 🔴 高 | 流式 `delta.reasoning` | Koog 的 StreamDelta 无 reasoning 字段，流式推理丢失 | 方案 D：MederiOpenAILLMClient 用 SanitizedStreamDelta + emitReasoningDelta |
| ✅ 无 | `tool_calls` snake_case | Koog `namingStrategy = SnakeCase` 自动处理 | - |
| ✅ 无 | `tool_calls[].id` 格式 | Koog 不校验格式 | - |
| ✅ 无 | vLLM 内部字段 | Koog `ignoreUnknownKeys` 忽略 | - |
| ✅ 无 | content/reasoning 回填 | 正常 max_tokens 下 content 始终有值 | - |

### 5.8 待确认事项（已查 Koog 1.1.1 源码确认）

#### 确认1：Koog 内部 Json 配置 ✅

**源码位置**：`AbstractOpenAILLMClient.kt` 第 115-121 行

```kotlin
private val defaultJson = Json {
    ignoreUnknownKeys = true
    isLenient = true
    encodeDefaults = true
    explicitNulls = false
    namingStrategy = JsonNamingStrategy.SnakeCase  // ← 关键
}
```

**结论**：
- `ignoreUnknownKeys = true` ✅——vLLM 内部字段（`prompt_logprobs`/`token_ids` 等）会被自动忽略
- `namingStrategy = SnakeCase` ✅——Koog 的 Kotlin 属性 `reasoningContent` 在 JSON 里期望的字段名是 **`reasoning_content`**（snake_case），不是 `reasoningContent`
- `toolCalls` → 期望 JSON 字段名 `tool_calls`（snake_case）——与 Hetzner 返回一致 ✅

**修正之前的分析**：Hetzner 返回 `reasoning`，Koog 期望 `reasoning_content`——差距是 `reasoning` vs `reasoning_content`（不只是少 "Content" 后缀，是 vLLM 用了简写 `reasoning` 而非完整的 `reasoning_content`）。

#### 确认2：OpenAIStreamDelta 没有 reasoningContent ✅

**源码位置**：`OpenAIDataModels.kt` 第 955-961 行

```kotlin
public class OpenAIStreamDelta(
    public val content: String? = null,
    public val refusal: String? = null,
    public val role: String? = null,
    public val toolCalls: List<OpenAIStreamToolCall>? = null
)
```

**结论**：`OpenAIStreamDelta` **确认只有 4 个字段，没有 `reasoningContent`**。流式模式下 Hetzner 的 `delta.reasoning` 会被 `ignoreUnknownKeys` 直接丢弃，**Koog 在流式层连解析 reasoning 的字段都没有**。

#### 确认3：KoogHttpClient.Factory 接口形状 ✅

**源码位置**：`KoogHttpClient.kt`

`KoogHttpClient` 接口：
```kotlin
public interface KoogHttpClient : AutoCloseable {
    suspend fun <T : Any, R : Any> post(path, requestBody, requestBodyType, responseType, ...): R
    fun <T : Any, R : Any, O : Any> sse(path, requestBody, ..., decodeStreamingResponse: (String) -> R, ...): Flow<O>
    
    public interface Factory {
        fun create(clientName, baseUrl, headers, ..., json: Json): KoogHttpClient
    }
}
```

**关键发现**：看 `AbstractOpenAILLMClient` 第 260-264 行：
```kotlin
httpClient.post<String, String>(path, requestBody).let(::decodeResponse)
```

`post` 的 `responseType` 是 `String::class`——**`KoogHttpClient.post()` 返回原始 JSON 字符串，由 `AbstractOpenAILLMClient` 自己调 `decodeResponse` 解析**。

同理，`sse()` 接受 `decodeStreamingResponse: (String) -> R` lambda——**SSE 原始字符串 chunk 先经过 lambda 解析**。

**这意味着**：自定义 `KoogHttpClient` 可以在 `post()` 返回前、`sse()` 的 `decodeStreamingResponse` 调用前，**拦截并重写原始 JSON 字符串**——把 `reasoning` 改成 `reasoning_content`，再让 Koog 正常解析。

### 5.9 确认后的标准化方案（最终）

基于源码确认，方案 B（自定义 `KoogHttpClient`）**完全可行**：

#### 实现原理

1. 实现 `KoogHttpClient` 接口（装饰器模式，委托给真实实现如 `KtorHttpClient`）
2. override `post()`：在返回 JSON 字符串前，把 `message.reasoning` 重写为 `message.reasoning_content`
3. override `sse()`：在每个 chunk 的原始字符串传给 `decodeStreamingResponse` 前，把 `delta.reasoning` 重写为 `delta.reasoning_content`

#### 非流式清洗

```
HTTP 响应 JSON → 自定义 KoogHttpClient.post() 拦截 → 
  把 "reasoning": "..." 重写为 "reasoning_content": "..." →
  返回修改后的 JSON 字符串 →
  AbstractOpenAILLMClient.decodeResponse() 用 defaultJson 解析 →
  OpenAIMessage.Assistant.reasoningContent 正确填充 ✅
```

#### 流式清洗

```
SSE chunk → 自定义 KoogHttpClient.sse() 拦截 →
  把 delta 里的 "reasoning": "..." 重写为 "reasoning_content": "..." →
  传给 decodeStreamingResponse →
  ⚠️ 但 OpenAIStreamDelta 没有 reasoningContent 字段 → 仍然丢弃
```

**流式问题**：即使重写字段名，`OpenAIStreamDelta` 没有 `reasoningContent` 字段，Koog 仍会丢弃。流式推理内容**无法通过字段名重写保留**——需要在自定义 `KoogHttpClient` 层直接提取 `delta.reasoning`，在 Koog 之外单独处理（如累积后作为流式 Reasoning 帧输出）。

#### 最终清洗需求定级（源码确认后）

| 优先级 | 清洗项 | Koog 期望字段名 | Hetzner 实际字段名 | 实现方案 | 可行性 |
|---|---|---|---|---|---|
| 🔴 高 | 非流式 reasoning | `reasoning_content` | `reasoning` | 自定义 `KoogHttpClient.post()` 拦截重写 | ✅ 可行（post 返回 String） |
| 🔴 高 | 流式 reasoning | `OpenAIStreamDelta` 无此字段 | `delta.reasoning` | 自定义 `KoogHttpClient.sse()` 拦截，Koog 之外提取 | ⚠️ 需绕过 Koog StreamDelta |
| ✅ 无 | `tool_calls` snake_case | `tool_calls`（SnakeCase 策略） | `tool_calls` | 无需清洗 | ✅ 匹配 |
| ✅ 无 | `tool_calls[].id` 格式 | `String`（不校验） | 三种格式 | 无需清洗 | ✅ 无害 |
| ✅ 无 | vLLM 内部字段 | `ignoreUnknownKeys=true` 忽略 | 9个字段 | 无需清洗 | ✅ 自动忽略 |
