## 必须修复的生产问题

### R01 [P1] SETUP/ACTION 生产入口仍然裸跑（RF-01）

`WorkspaceEnvironmentService.kt:139-145` 在 permissions=null 时直接 ProcessBuilder，不套任何 OS 沙盒，注释明确以兼容测试为由保留。真实 `WorkspaceManager.runWorkspaceAction:2369-2373` 不传 permissions；首次发送的 `prepareSessionWorkspace:237` 也不传，最后传入 setup 的仍为 null。因此不仅是测试兼容分支，真实 AiCore/Core API 就会走到它。

**独立复现：** `productionActionMustEnforceProjectDeniedPaths` 使用真实 `Mederi.create`、持久项目黑名单、saveProjectEnvironment、workspaces.runWorkspaceAction，拒绝文件从 original 被改为 overwritten。

必须在生产装配构造真实权限与审批上下文，全部脚本复用 ShellTools 的后端、拒绝规则和回收，不允许 null 裸跑。现有测试只给 EnvironmentService 手动传 permissions，覆盖不到生产遗漏。

### R02 [P1] ShellTools 重建沙盒时仍丢工作区凭证（RF-02）

`ShellTools.kt:76-78` 有 grant 时调用四参数 CommandSandbox 构造，verifiedWorkspaceRoot 为 null，完全忽略 ExecutionPermissions 已有的 provider。Mederi 的受管目录位于 runtime/controlRoot 内；失去精确例外后默认命令不能写受管 checkout，精确产物根及映射拒绝规则也不能沿同一凭证应用。

把同一经校验的工作区凭证传到实际启动后端。RF-02 的 fake LLM 只调用 write_file，无法证明真实 bash/verify 可在默认宿主目录写文件。

### R03 [P1] 所谓动态凭证一直读发送时的旧工作区代次（RF-02）

`TurnExecutor.kt:462-464` provider 捕获不可变 execWs，每次仅用同一份 generation 构造新对象；`buildVerifiedWorkspaceRoot:1240-1254` 不重新读取 WorkspaceStore/绑定。`ExecutionPermissions.validateGrant` 比较该 provider 的 generation，因此无法观察真正的代次变化。身份创建失败还被 getOrNull 静默降级。

真实工作区创建分支等操作会递增 generation。已发起的授权等待在代次改变后仍可能通过旧 provider 完成写入。现有 `staleWorkspaceGrantFailsThroughActualToolFactory` 实际手工 new FileSystemTools，自造会变化的 provider，绕开了真实 TurnExecutor 的固定闭包，未经过 ToolFactory。

应由唯一执行协调器从真实绑定/Store 重验代次与身份，失败即停；用真实发送/工具装配获得旧 grant，再改变真实 Store 验证失效。

### R04 [P1] 项目路径黑名单未映射到受管副本文件 API（RF-01/02）

`WorkspaceManager.enforceReadPolicy:61-70` 和 `listWorkspaceFiles:2203-2212` 仅用原始绝对 deniedPaths，projectDirs 为空且没有工作区映射。Local 的 secret.txt 被拒绝，不代表 managed/checkout/secret.txt 被拒绝。

**独立复现：** `managedFileApiMustRemapProjectBlacklist` 创建真实项目、持久拒绝 Local secret.txt，准备 managed checkout，调用真实 workspaces.readWorkspaceFile，成功读出 fake protected content。

不仅修 API：SandboxPaths 的映射依赖 projectDirs 为原项目根，而 TurnExecutor 当前传的是 managed workingDir，也要复核工具读写和 shell 同一映射来源。

### R05 [P1] 正式 linked 恢复会写穿末级符号链接（RF-03/06）

`WorkspaceSnapshotService.kt:507-519` 先 worktree add 检出 HEAD，`:579-583` 对快照 FILE 直接 writeBytes。祖先检查不包括 dest 本身。若 HEAD 的 node 是指向外部文件的 symlink，未提交状态把 node 换为普通文件，归档快照为 FILE；恢复检出 HEAD 后又出现 symlink，writeBytes 写到外部目标。

**独立复现：** `linkedRestoreMustNotWriteThroughHeadLeafSymlink` 外部文件由 external-newer 被覆盖为 snapshot-regular-file。

必须 NOFOLLOW 处理末级、正确实现文件/目录/链接类型替换，再核验目标内容。不得仅禁止合法 Git symlink。

### R06 [P1] 归档恢复会删除快照之后的新改动（RF-04）

`WorkspaceManager.kt:1259-1263` 只判断 checkout 存在且有 snapshotId，直接重试 worktree remove --force，没有比较当前后像、取得管理意图或保存新改动。

**独立复现：** `archiveRecoveryMustPreserveChangesAfterSnapshot` 在真实 archive 已持久快照日志后注入失败，模拟停机期间写入 after-snapshot，再由新 Manager 扫描；新文件与整个 checkout 被删除，快照不包含新文件。

任何未知新改动必须保留并转 RECOVERY_REQUIRED；恢复也必须走真实管理协调与身份验证。

### R07 [P1] 只要是 Git 仓库就把未完成恢复宣告成功（RF-04/06）

`WorkspaceManager.kt:1299-1325` 仅执行 rev-parse --is-inside-work-tree。worktree 注册成功但文件/index 物化中断时仍 READY/SUCCEEDED，没有验证 snapshot 内容、index、HEAD/common-dir 注册或阶段后像。

**独立复现：** `interruptedRestoreMustNotDeclareIncompleteCheckoutReady` 真实 restore 注册 worktree 后因悬空 HEAD symlink 物化失败，scanner 把仅有 HEAD 残留的 checkout 标为 READY，而 snapshot-regular-file 内容从未恢复。

必须依据真实可验证阶段重放或隔离，不能以“Git 可用”代替完整恢复证明。

### R08 [P1] Handoff 成功与会话绑定仍非原子（RF-04）

`WorkspaceManager.kt:1002-1010` 分别写源 Workspace、目标 Workspace、SUCCEEDED operation，最后才 updateWorkspaceBinding，没有调用已有 commitBinding CAS。最后一步失败时源已清理、操作已成功但会话仍指向源；scanner 只看未完成操作，不再修复 SUCCEEDED。

应对 Workspace generation、Session 绑定/associated worktree 和 operation 使用同库事务/CAS，补真实 SQLite 故障/reopen 测试。当前所谓 every-real-boundary 只在内存 Store 的一次 saveWorkspace 前注入，并非全部边界。

### R09 [P1] 恢复扫描仍无生产初始化调用（RF-04）

`WorkspaceManager.kt:1116` 的 scanAndRecoverPendingOperations 只有定义与 JVM 测试调用；core 和 app/shared 的生产代码没有调用。真实重启不会像测试一样主动扫描，RUNNING/TRANSFERRING/ARCHIVING 残留无法自动归位。

修复恢复算法后，挂在两个 interface 共用的 Core/AiCore 初始化门禁，并避免 readiness 前放行新执行。不能挂 desktop main 或以 UI 手动进入某个会话代替启动恢复。

### R10 [P1] Handoff 日志缺真实后像，回滚会伪装已恢复（RF-04）

`WorkspaceManager.kt:852-859`、`:941-948` 只记 SNAPSHOT/CLEAN_SOURCE，affectedPaths 为空；detach/switch/copy/setup 等副作用没有逐阶段意图与可验证后像。恢复 `:1191-1202` 将空 affectedPaths 传给 rollback 后可标双方 READY，但没有恢复复制的工作树文件/分支。

日志必须在每个实际 mutation 前后落盘，记录文件类型/hash/mode/ref/index 等需要恢复的事实。补实际各边界崩溃与真实 SQLite reopen，不是人工拼一条理想 RUNNING 记录。

### R11 [P1] 后台命令及环境操作没有独立执行租约（RF-07）

唯一生产 acquireExecutionLease 调用在 `TurnExecutor.kt:1292`，`:1609` 随 turn 结束释放。`ShellTools.kt:155-169` 把后台进程交给 BackgroundTaskManager 后没有持有进程生命周期租约；setup/action 同样没有。

父 turn 结束但后台命令还在写文件时，归档看见计数为零，可快照并强删 checkout，晚于快照的写入丢失。现有 RF-07 测试手工 acquire 一个租约，而不是启动真实 turn/后台命令，因此通过不能说明接线完整。

租约必须跟随真实进程/子代理/verify/setup/action 生命周期，退出或 stop/join 后释放，管理意图阻止新执行。

### R12 [P1] 清源仅核工作树文本，未保护新增暂存内容（RF-05）

`WorkspaceManager.kt:1060-1076` 只核 exists 和 FILE hash，`:1083-1084` 随后执行 git restore --staged --worktree，没有核 snapshot 后的 index/ref/mode/linkTarget。

捕获快照后，用户把新内容 B git add 暂存，再将工作树文本恢复为快照 A：hash 检查仍过，git restore 清掉没有进入快照的 index B。符号链接目标和执行位变化也未比较。

清源前全量核对工作树、index 与 ref 基线；未知改动零覆盖。回归需从真实 Handoff 的 snapshot→cleanup 窗口注入，不只调用公开化的内部 clean helper。

### R13 [P1] UI 的 Worktree→Local 交接不可用（RF-08）

`WorkspaceViewModel.kt:392` 和 `:424` 把目标写死 MANAGED_WORKTREE。真实 Manager `:618-620` 明确拒绝源目标同类型。因此 Worktree 会话点击迁移时请求非法，且预览失败无回显，用户看来按钮没反应。

必须按源类型确定/提供目标选择，预览与执行使用同一目标。新 UI 测试却用 MANAGED 源预览 MANAGED 目标，Mock 接受了真实 Manager 拒绝的请求，反向掩盖缺陷。

### R14 [P1] 恢复、固定及环境能力仍没有真实 UI 入口（RF-08）

生产 UI 中 `WorkspaceViewModel.previewRecovery:505`、`setPinned:498` 没有调用方；Recovery Dialog 虽挂载但用户打不开。环境编辑/动作、宿主 Worktree 设置也没有真实 UI 消费相应 API。管理列表挂载不能代表完整功能入口。

必须接通 Sidebar/状态条/项目或工作区设置等真实按钮，包括窄屏；测试从真实界面点击，而不是直接调 VM。

### R15 [P2] 对话框异步响应跨会话污染，错误被静默忽略（RF-08）

`WorkspaceViewModel.kt:394/443/468/512` 异步完成无条件写 _dialogState，attach `:2036` 不失效请求/清理归属。A 的预览未完成时切 B，A 响应在 B 显示；execute `:417` 读取当前 B，用 A token 提交。关闭之后旧响应也可重新打开面板。

openHandoff/归档只 onSuccess，execute 失败只恢复 loading；未显示权限拒绝/stale/dirty/IO 错误。Workspace.kt:598-607 未把 loading 传给 Handoff 面板，执行期间仍可刷新替换预览。

面板绑定 owner/session/request generation，dismiss/切换失效旧响应；显示本地化错误并保持可重试状态，实际界面体现 busy 与冲突。
